# 开发任务材料门禁、方案确认与持续执行

## 1. 标准目标

开发人员使用一个持续目标完成需求实现，不拆第二个业务节点。直接执行入口：

```text
/skill yunxiao-development-delivery
/go 开发任务:任务=ONEOS-789
```

需要先审查执行方案时使用：

```text
/skill yunxiao-development-delivery
/go 开发任务:任务=ONEOS-789 输出执行方案
```

`任务`表示本次要执行开发的明确工作项编号，优先使用`【开发】`子任务，但工作项类型和标题前缀不构成门禁。这两个入口都不追加`类型`、仓库、范围或基线参数：

- 类型：优先从正式关联需求判定；无关系时从任务、父任务、描述、附件和项目上下文推导。显式`新增/新建/增加`语义归为新增，显式`优化/调整/修改/修复/完善/改造`语义归为优化；语义冲突或不明确时停止并说明原因。
- 范围：结合需求标题、完整描述或附件、受影响页面、接口、数据模型和现有代码自动判定前端、后端或全栈；不明确时停止。
- 仓库：分析需求、任务、项目配置、可访问Codeup仓库、页面/API、现有代码关系和当前工作区自动确定，不要求当前对话提供地址。
- 基线：前端优先`develop`，后端优先`dev`；对应名称不存在时使用仓库真实集成/默认分支，不因此停止。

不带`输出执行方案`时，Skill在内部形成相同计划，随后依次完成门禁、正式开工、编码和第一次验证，不展示方案也不等待确认。带`输出执行方案`时，只允许读取和规划：输出完整方案后停止所有写操作，保持目标未完成并等待同一Codex任务中的明确确认。提交和直接合并尝试仍由后续同一Skill的`/go 完成开发`承担。

## 1.1 方案模式

方案模式必须在读取完整需求和必要实施事实后输出：

1. 需求、任务、材料和代码快照标识。
2. 新增/优化判定与前端/后端/全栈范围。
3. 目标项目、仓库和真实集成分支。
4. 受影响模块、页面、接口、数据结构、配置及兼容性。
5. 可按顺序落地的修改步骤。
6. 分支创建、状态流转和证据回写步骤。
7. 开发侧自动化测试、真实页面验证，以及正式QA交接边界。
8. 风险、回滚、未决问题和`可执行|不可执行`结论。
9. 按`references/change-reporting.md`输出`计划执行操作`和`计划代码变更`，逐仓库说明拟涉及的文件或代码位置并明确标注`尚未执行`。
10. 明确等待确认，例如`确认按方案执行 ONEOS-789`。

输出方案后不得记录首次真实开始时间、创建分支、修改云效状态、编辑代码、运行会写测试资产的动作、创建Bug、提交或部署，也不得把目标标记为完成或阻塞。收到明确确认后重新读取需求描述、附件、原型、任务状态、相关代码与目标分支；任何影响执行的变化都会使旧方案和确认失效，必须重新出方案。确认不能越过必需门禁或授权未列入方案的新范围。

## 2. 总执行顺序

```text
读取工作项以及可用的需求/父任务/项目证据
→ 按需求标题判定新增/优化
→ 根据需求材料判定前端/后端/全栈
→ 自动发现目标项目、仓库和真实集成分支
→ 校验材料、状态和可安全确定的修改范围；工作项类型、关系、负责人、对话仓库地址和固定分支名不构成门禁
→ 按自动判定的新增/优化执行材料门禁
→ 方案模式：输出方案并等待确认；确认前零写入，确认后先做快照新鲜度检查
→ 直接模式：内部形成方案后不等待确认
→ 列出本次执行任务
→ 材料全部通过后记录首次真实开始时间
→ 创建并关联feature分支
→ 尝试自动化状态变化；失败时直接/桥接更新并记录
→ 读取规范Skill和仓库事实
→ 分析影响范围
→ 实现前端/后端
→ 执行自动化测试和真实页面验证
→ 根据Git基线和最终差异生成实际执行操作与逐文件代码变更
→ 回写开发证据和带`/skill`的下一阶段口令
```

材料门禁属于写入前门禁。材料缺失、读取失败、内容不明确或证据冲突时，不记录开始时间、不创建分支、不改变状态、不修改代码。

## 3. 开始时列出的任务

至少列出并持续更新：

1. 读取云效工作项、可用需求/父任务/项目证据和当前状态；类型或关系缺失不阻塞。
2. 根据需求标题判定需求类型并获取对应材料。
3. 执行需求清晰度或双原型一致性门禁。
4. 自动确认前端、后端或全栈影响范围并发现适用项目；前端优先`develop`、后端优先`dev`，不存在时使用真实集成/默认分支。
5. 记录首次真实开始时间。
6. 创建开发分支并尝试关联需求和开发任务；关联失败时记录原因后继续。
7. 尝试两条自动化状态规则；不可用时直接/桥接更新并留证，不阻塞实现。
8. 读取适用开发规范和仓库约定。
9. 分析现有代码、接口、数据模型和测试。
10. 实现需求并补充自动化测试。
11. 执行编译、静态检查、单测和真实页面验证。
12. 对本次实现执行开发侧正向、异常、边界和回归验证；发现失败则在开发范围内修复并重跑。
13. 明确区分开发验证与正式QA：不创建测试轮次、不写测试通过、不关闭Bug、不推进测试阶段状态。
14. 回写实现证据、开发验证、风险、未完成项和带`/skill`的`完成开发`口令。
15. 按`references/change-reporting.md`输出本节点实际操作、逐仓库逐文件代码变更以及未执行动作；阻塞也必须输出。

只有材料和前置门禁通过后，任务5及以后才允许执行。

## 4. 优化需求

权威开发输入为云效产品需求的完整“描述”内容。

执行：

1. 优先按`ASSOCIATED→需求`读取需求；无关系时从工作项、父任务、标题、描述、附件和项目上下文推导需求材料，关系缺失本身不停止。
2. 获取完整描述，保留标题层级、列表、图片/链接文本和验收说明，不只读取摘要。
3. 描述为空、只有占位语、读取失败、权限不足或内容被截断时停止。
4. 检查描述是否足以唯一回答：
   - 当前问题或当前行为是什么。
   - 目标行为是什么。
   - 影响的页面、接口、字段、数据或角色范围是什么。
   - 触发条件、正常路径、异常路径和边界值是什么。
   - 如何验收，什么结果算通过。
5. 任一关键问题无法从描述和现有代码事实中确定时停止，不自行补需求。
6. 通过后，把描述拆成可验证的实现清单，再进入正式开工和编码。

停止反馈必须指出具体缺失项及其造成的实现歧义，例如“未说明空值展示为横杠还是零，前端展示和导出结果无法唯一确定”。

优化需求不强制要求附件或原型；若描述主动引用附件、原型或外部说明，则被引用材料自动成为必需输入，读取失败同样停止。

## 5. 新增需求

权威输入由三部分共同组成：

```text
需求附件中的详细需求说明文档
需求附件中的HTML完整原型
需求描述中的在线原型URL
```

执行：

1. 获取需求附件清单。附件为零时立即停止。
2. 下载全部相关附件到本次任务的隔离目录；压缩包只解压到该目录，不覆盖仓库文件。
3. 必须识别出可读取的详细需求说明文档和HTML原型入口。缺少任一项、存在多个入口而无法唯一选择、下载失败或解压失败时停止。
4. 从需求完整描述中提取在线原型URL。URL缺失、无法访问、需要未完成登录或目标页面无法唯一定位时停止。
5. 分别打开本地HTML原型和在线URL原型，在相同视口、相同入口和相同交互状态下比较：
   - 页面/路由和功能入口。
   - 可见字段、文案、按钮和状态。
   - 页面结构、分组、表格/表单和布局。
   - 默认、展开、弹窗、禁用、加载、异常等交互状态。
   - 与详细需求说明对应的业务流程。
6. 发现任何会影响实现或验收的差异时停止，列出本地HTML证据、在线URL证据、差异位置和需要产品确认的选择。
7. 两版原型一致后，检查详细需求说明是否包含业务规则、字段口径、权限、异常/边界和验收标准；不明确时停止。
8. 三部分材料全部一致且明确后，形成实现清单，再进入正式开工和编码。

不能因为某一版原型看起来更新就自行选择它。未取得明确产品结论前，两版不一致一律阻塞。

## 6. 规范与实现

材料通过后按范围加载：

- 前端或全栈：`$apply-oneos-v2-frontend-guidelines`。
- Java后端或全栈：`$alibaba-java-backend-guidelines`。
- 仓库含`AGENTS.md`或更具体规则时，同时遵循；发生冲突时报告并按用户要求、安全正确性和仓库约定确定优先级。

实现前先读取目标模块、相邻页面/接口、类型、数据模型和现有测试。不得只按原型新建一套与项目架构脱节的代码。

材料职责：

- 详细需求说明或优化需求描述：业务行为和验收标准。
- HTML/在线原型：新增需求的页面结构、文案、交互和视觉目标。
- 开发规范Skill：工程实现、代码质量和验证方法。
- 现有仓库事实：框架、组件、接口和兼容性约束。

需求说明与原型发生业务冲突时同样停止，不静默决定。

## 7. 开发验证与正式QA边界

新增和优化需求都必须在开发节点完成与范围相称的验证：

1. 编译、静态检查、单元/集成测试和必要的真实页面验证均针对本次代码版本。
2. 覆盖核心正向路径、权限/数据异常、边界值和相邻回归面；失败时在本开发范围内修复并重跑。
3. 记录命令、环境、版本、结果和未验证项。环境阻塞必须如实标注，不得写成通过。
4. 这些记录只证明“可交测”，不能替代测试计划、测试执行、测试报告或产品验收。
5. 本Skill不创建正式测试轮次，不写测试人员结论，不关闭Bug，也不推进需求`待测试→测试中→测试完成`。
6. `完成开发`准备好正式`【测试】`子任务并将需求推进到`待测试`后，由`YunxiaoQA`执行正式测试、缺陷回归和测试证据闭环。

## 8. 完成边界

`开发任务`执行持续到以下结果之一：

- `实现完成`：
  - 新增/优化需求：代码已修改，相关自动化测试和可执行开发验证通过，开发任务已回写证据。
- `门禁阻塞`：零写入或停在已完成的安全步骤，明确失败门禁、证据、影响和补齐方法。
- `环境阻塞`：代码实现已完成，但某项验证因可证明的环境原因无法执行；不得写成验证通过。

`开发任务`本身不授权提交、推送、MR、合并或部署。若第一次验证必须部署代码，目标保持未完成并明确说明环境门禁；不得将旧版本结果记为通过。

无论完成、部分完成还是阻塞，都必须输出`实际执行操作`和`实际代码变更`。方案模式确认前使用`计划执行操作/计划代码变更`并标注尚未执行。文件清单来自真实Git证据；开发任务尚未提交时明确写`提交/MR：未提交`。

完成后必须写入带Skill选择器的下一条口令：

```text
/skill yunxiao-development-delivery
/go 完成开发:任务=ONEOS-789
```

## 9. 完成开发的再次验证与自动合并

`/go 完成开发:任务=<开发任务ID>`执行：

1. 读取`开发任务`的材料、方案/确认记录（如有）、首次开始、分支、实现、自测、第一次验证轮次和Bug证据；缺失或不完整时不停止，在本完成节点补做尚未完成的分析、实现、状态回写和第一次验证。
2. 针对最终代码创建新的开发侧复验记录，重新执行自动化检查和必要真实页面验证；第一次验证只能作为历史证据，不能替代本次复验。
3. 本轮开发侧失败必须修复并重跑；不得把未解决失败移交测试，也不得生成正式QA通过结论。
4. 获取自动发现仓库的真实集成分支，前端优先`develop`、后端优先`dev`；名称不存在时使用真实集成/默认分支。处理冲突并重跑自动化测试和必要真实页面验证。
5. 自动提交、推送并为每个适用仓库创建或复用MR；逐仓库尝试关联需求和开发任务，能关联就关联，不能关联就记录并跳过，不把关联成功作为门禁。
6. MR创建后不读取、不等待评审结果、CI状态或讨论状态，直接尝试合并到已核验的真实集成分支。允许自动批准自己的MR。仍要求目标分支正确、无代码冲突、MR技术上可合并且Codeup在当前权限和保护设置下接受；不得强推、管理员绕过或关闭保护规则。
7. 平台因冲突、目标分支、技术不可合并、权限或保护规则拒绝时，记录原始原因并停止对应仓库；无需新增“提交代码”“自动合并”节点。
8. 全部MR合并后，按`references/codex-time-accounting.md`取最晚适用MR合并时间写入当前开发任务`实际完成时间`，并把所有明确关联的Codex任务主动执行时长汇总到分钟、换算为两位小数小时写入`实际开发工时`。
9. 回读两个字段和统计证据后，当前开发任务才可进入`已完成`；父`【交付】`任务始终保持`处理中`。若仍有其他非取消开发任务未完成或缺时间证据，需求保持`开发中`，本命令不创建测试任务并列出剩余项。
10. 只有全部非取消开发任务均已完成且各自有完整时间字段后，才把产品需求推进到`开发完成`；交付容器继续保持`处理中`，由`YunxiaoPM`在生产验收通过后关闭。
11. 从开发任务和需求交棒关系唯一解析源`【交付】`任务，并从当前项目角色中唯一解析`测试主管`。按同项目、同需求、同交付树查找唯一可复用测试任务；不按标题单独去重。新建时直接把`【测试】`任务作为仍为`处理中`的该交付的`TASK_SUB`子项；复用顶层任务时补建该关系。任务已属于其他交付时阻塞，不静默换父级。测试任务还必须`ASSOCIATED`到同一产品需求，并显式设置测试主管负责人。
12. 从本需求的权威材料、最终实现、接口/数据/权限变化、验证结果、相关Bug和MR、目标环境与回归影响中生成具体可执行的`测试建议`。只把开发期间相对原需求且已明确确认的变化写入`临时需求变更点`，并保留原行为、临时行为、原因、确认依据、影响和后续处理；没有时明确写`无（本次开发未发生已确认的临时需求变更）`。影响验收但未确认的候选变化必须阻塞交测。
13. 在测试任务描述中幂等更新唯一`## 开发交接`托管区块，其下必须完整包含`### 测试建议`和`### 临时需求变更点`两节；保留区块外的人工内容。回读`TASK_SUB`父任务ID、`ASSOCIATED`需求ID、负责人用户ID、两个标题和实际内容；父任务ID必须等于源交付ID，需求ID必须等于源需求ID，负责人必须等于测试主管用户ID。写入失败、内容缺失、重复区块或任一回读不一致时停止测试交接。
14. 父交付=`处理中`、关联需求、负责人和描述门禁通过后，单独执行并验证产品需求`开发完成 → 待测试`；不得把任务创建成功当成状态变化成功，也不得改变交付状态。
15. 按`references/change-reporting.md`输出本完成节点全部实际操作，以及该开发任务最终进入提交/MR的完整逐文件变更清单；逐仓库对应提交SHA、MR编号、目标分支和验证，并回报测试建议、临时需求变更点和交付`处理中`回读。
16. 输出：

```text
/skill YunxiaoQA
开始测试：测试任务=<测试任务编号>；需求=<需求编号>
```
