# 开发口语化口令

## 接收产品交棒

```text
接收产品交棒:需求=ONEOSP-123 交付任务=ONEOS-456
```

先按编号读取真实状态和关系。标准输入应为需求=`待开发`、`【交付】`任务负责人=何斐、交付`ASSOCIATED→需求`。产品Skill不会创建`【开发】`任务：若本口令已给负责人/仓库/范围，则幂等创建或复用开发任务；缺参时只回报已接收和待补参数，不猜人、不猜仓库。

本口令只验收交棒，不分配开发任务。

## 分配任务

```text
分配任务:任务=ONEOS-456 负责人=李振 计划开始=2026-07-27 计划完成=2026-07-28 预计工时=8
```

使用空格分隔参数，不要求输入分号。`任务=ONEOS-456`固定表示YunxiaoPMapp交付的`【交付】`任务，`负责人=李振`表示开发任务负责人：

1. 按编号读取交付任务并反查需求，验收需求=`待开发`、交付任务=`待处理`或幂等的`已分配`交棒。
2. 尝试解析并设置李振；负责人无法唯一解析时不停止，复用任务则保留原负责人，新建任务则允许暂不设置并在结果中报告。校验日期；预计工时可不填写，填写时必须大于0。
3. 在该交付下创建或复用`【开发】<需求标题>`子任务。
4. 写负责人、计划开始、计划完成、预计工时，任务保持`待处理`。
5. 同时建立`TASK_SUB→【交付】`和`ASSOCIATED→需求`，缺少任一关系都视为分配失败。
6. 在开发任务描述中幂等维护：

```text
## 下一阶段
/skill yunxiao-development-delivery
/go 开始开发:任务=<开发任务编号>
```

不得追加类型、仓库、范围或基线参数，也不得覆盖原有业务描述。
7. 重新读取字段、两条正式关系和下一阶段命令。
8. 全部字段、正式关系和下一阶段命令回读通过后，交付任务`待处理 → 已分配`；需求保持`待开发`，开发任务保持`待处理`。交付任务仍由何斐负责，不改其计划或工时；已经`已分配`、`处理中`或`已完成`时只按幂等结果回报，不回退状态。

仓库和前后端范围不写入口令。开始开发时分析需求、页面、接口、数据、项目配置、现有代码关系和可访问Codeup仓库，自动判断需要在哪个项目操作；不要求在当前对话提供项目地址。若交付下存在多条开发任务而无法判断，使用：

```text
分配任务:任务=ONEOS-456 开发任务=ONEOS-789 负责人=李振 计划开始=2026-07-27 计划完成=2026-07-28 预计工时=8
```

## 开始开发

```text
/skill yunxiao-development-delivery
/go 开始开发:任务=ONEOS-789
```

这里的`任务`表示本次要执行开发的明确工作项编号，优先使用分配后返回的`【开发】`任务，但不是开发子任务也不构成门禁。`/go`在同一个开始开发节点中持续执行，不再拆分“实现需求”口令：

1. 先列出材料、开工、分支、实现、测试和回写任务。
2. 优先从正式关系读取需求完整标题；没有关系时从任务、父任务、描述、附件和项目上下文推导。标题含明确`新增/新建/增加`语义时判为新增，含明确`优化/调整/修改/修复/完善/改造`语义时判为优化；关系缺失本身不阻塞，只有材料语义冲突或无法判定类型时停止并反馈。
3. 从需求标题、完整描述/附件、受影响页面、接口、数据模型和现有代码事实自动判定前端、后端或全栈。无法唯一确定时停止并说明冲突，不要求开发人员补`范围=`参数。
4. 分析需求、任务、父任务、附件、页面、接口、数据、项目配置、现有代码关系、可访问Codeup仓库和当前工作区，自动判断前端、后端项目；不从对话索要项目地址。只有发现多个冲突候选且继续会改错项目时才停止。
5. `任务=<ID>`只要求能读取到明确工作项，不要求它是`【开发】`子任务，也不要求存在`TASK_SUB→【交付】`或`ASSOCIATED→需求`。有关系时优先使用；无关系时从任务和项目证据推导需求及范围并报告追溯缺口。初次任务通常为`需求=待开发、交付=已分配、开发任务=待处理`；同一交付下已有兄弟任务开工时允许`需求=开发中、交付=处理中、当前开发任务=待处理`；续跑按实际状态幂等处理。
6. 优化需求读取云效需求完整描述；为空、获取失败、只有占位内容或无法明确实现与验收时停止并反馈具体缺口。
7. 新增需求先下载附件，必须得到详细需求文档和HTML原型，并从需求描述取得在线原型URL；无附件、材料缺失、URL不可访问或两版原型不一致时停止并反馈证据。
8. 材料门禁通过后，初次开工记录首次真实开始时间；优先从前端`develop`、后端`dev`创建分支。对应名称不存在时不停止，读取仓库真实集成/默认分支并使用，再关联`feature/<需求或任务编号>`；合法续跑复用原时间、分支和已验证检查点。
9. 优先由云效自动化规则完成：
   - 开发任务：`待处理 → 处理中`
   - 第一个开发任务开工时，交付任务：`已分配 → 处理中`
   - 产品需求首次开工：`待开发 → 开发中`
   - 需求和交付已经因兄弟任务处于`开发中/处理中`时，只更新当前开发任务，不重复推动父级状态。
10. 等待5–30秒检查状态和日志。规则缺失、停用或失败时不停止，使用可审计的直接更新或桥接完成相同状态变化，并明确记录实际方式。
11. 按自动判定的范围加载前端/后端规范Skill，读取现有代码后直接实现需求并验证。
12. 若为优化需求，`/go`结束于本地实现和验证完成。
13. 若为新增需求，继续调用`$yunxiao-test-management`：
   - 优先按`ASSOCIATED→需求`取得需求；没有关系时使用前述任务与项目证据推导并记录依据，再在同项目、同迭代中用需求完整名称精确匹配验证测试用例；名称必须完全一致，不使用包含、关键词或相似度匹配。
   - 零个同名用例时停止；多个不同用例ID全部纳入本轮，若跨需求、跨迭代或跨用例包冲突则停止并列出冲突。
   - 确认测试页面运行的是本次代码版本；旧版本结果不得作为验收证据。
   - 执行全部同名验证用例；失败时去重后自动创建Bug，标题固定为`[<开发任务ID>]<Bug描述>`，并同时关联需求、开发任务和原测试用例。
   - 开发侧修复后只把Bug改为`已修复`；测试侧复测原用例并把结果写入本次计划/轮次，通过后关闭Bug，失败则重新打开。
   - 循环修复和复测，直到关联用例全部通过、每次历史失败均有通过的复测证据、当前需求范围内活动Bug和“已修复但未复测”Bug均为0。
14. 新增需求没有同名验证用例，或测试目标未包含本次代码时，`/go`保持未完成并明确反馈阻塞；不得伪造通过结果。
15. `开始开发`不提交、推送、建MR、合并或部署。通过后在任务描述中幂等写入：

```text
## 下一阶段
/skill yunxiao-development-delivery
/go 完成开发:任务=<开发任务编号>
```

测试执行只更新本次计划/轮次的执行结果，不修改、关闭、停用、归档或废弃可复用测试用例。

详细材料门禁与任务清单见`references/implementation-materials.md`。

新增需求完成回报必须包含：

```text
用例总数：
通过/失败/阻塞/未执行：
历史失败复测证据：
活动Bug：
已修复但未复测Bug：
用例/Bug闭环：通过|未通过
```

## 批量实现我的开发任务

标准口令：

```text
/go 实现所有负责人是我的开发任务
```

以下相似表达按同一入口处理：

```text
/go 实现我的全部开发任务
/go 开发我负责的所有开发任务
```

需要限定范围时：

```text
/go 实现所有负责人是我的开发任务 项目=统一运营管理平台PC端 迭代=V1.3
```

执行约定：

1. 解析当前登录云效账号，查询负责人为本人、标题以`【开发】`开头、状态为`待处理`或`处理中`的有效任务。
2. 固定本次任务快照并先输出列表；运行期间新分配任务留到下次。
3. 从任务、可用需求/父任务、材料和项目上下文自动判定类型与范围，再从项目配置、Codeup、页面/API和代码事实自动发现目标仓库与真实集成分支；不读取或要求对话提供仓库地址。
4. 逐条调用现有`/go 开始开发:任务=<开发任务编号>`处理器，不复制或放宽单任务规则；某任务缺少所需项目地址时只阻塞该任务并继续下一条。
5. 每条任务使用独立worktree；一个任务的未提交改动不得进入另一个任务。
6. 单个任务门禁失败时停止该任务，记录失败原因并继续下一个。
7. 全部任务均尝试后，列出完成任务以及所有未实现任务、失败门禁、当前值和处理建议。
8. 只要仍有未实现任务，“实现所有”的目标就保持未完成；补齐条件后使用`/go 继续实现我的开发任务`续跑原批次。

完整规则和汇总格式见`references/batch-execution.md`。

产品交棒未完成时使用：

```text
/skill YunxiaoPMapp
交棒开发:ONEOSP-123 交付任务=ONEOS-456
```

## 完成开发

```text
/skill yunxiao-development-delivery
/go 完成开发:任务=ONEOS-789
```

这里的`任务`仍表示`【开发】`子任务。该节点连续完成以下动作，不拆成“提交代码”“创建MR”“自动合并MR”三个业务节点：

1. 重新读取工作项、需求/任务证据、首次真实开始时间、分支、第一次验证记录和Bug；`开始开发`证据缺失或不完整时不停止，在本节点补做尚未完成的分析、实现、开工回写和第一次验证。
2. 新增需求按`项目+迭代+需求完整名称`再次精确匹配同名验证测试用例，创建独立于第一次的复验轮次；不得复用第一次结果冒充本轮已执行。
3. 复验失败时创建或复用标题为`[<开发任务ID>]<Bug描述>`的Bug，开发修复、测试复测，直到本轮失败/阻塞/未执行为0，且没有当前范围Bug或全部Bug已关闭。
4. 汇总全部适用仓库，获取最新真实集成分支并停止处理代码冲突；重跑本Skill范围内的代码检查后自动提交、推送、创建或复用MR。逐仓库尝试把分支/MR关联需求和开发任务；能关联就关联，不能关联则记录`跳过/失败原因`并继续，不把关联结果作为合并或完成门禁。
5. MR创建后不读取、不等待代码评审、CI结果或讨论状态，直接尝试合并到自动发现并核验过的真实集成分支；不要求新的自动合并口令。允许在Codeup支持且当前账号有权限时自动批准自己的MR，但批准不是前置条件。
6. 仅代码冲突、错误目标分支、MR技术上不可合并或Codeup按当前权限/保护设置拒绝合并时停止。记录平台原始原因；不得强推、管理员绕过或关闭保护规则。
7. 全部适用仓库MR合并后，取这些MR中最晚的`merged_at`，按项目时区写入当前开发任务`实际完成时间`。
8. 查找所有能通过当前开发任务编号、正式Bug关系或批量分段证明相关的Codex任务；按任务ID和分段ID去重，汇总平台记录的主动执行秒数。总秒数统一四舍五入到分钟，再用`总分钟数÷60`换算为两位小数小时，写入`实际开发工时`。
9. 回读实际完成时间、实际开发工时和统计证据。缺任务时长、混合任务无法分段、只能取得自然时间跨度、字段单位/精度不符或回读失败时，不把开发任务改为`已完成`。
10. 统计回读通过后，当前开发任务进入`已完成`，其余非取消开发任务未完成时父交付任务保持`处理中`；再核验全部非取消开发任务均已完成且各自具有实际完成时间和实际工时，父`【交付】`任务才进入`已完成`，产品需求才进入`开发完成`。
11. 创建或复用唯一`【测试】`任务。项目中恰好一个`测试主管`时自动指派；无人或多人时保留已有负责人，或让新任务暂不设置负责人并列出候选，不阻塞后续交接。
12. “创建/复用测试任务”和“产品需求`开发完成 → 待测试`”是两个独立动作。测试任务回读通过后再执行状态变化，不得用测试任务存在替代状态变化证据。
13. 写入下一阶段命令：

```text
## 下一阶段
/skill yunxiao-test-management
提交测试:需求=<需求编号> 测试任务=<测试任务编号> test流水线=<流水线> 执行ID=<执行ID或待填写>
```

## 修复单个Bug

```text
/skill yunxiao-development-delivery
修复bug:BUG-123
```

这一条命令合并原来的“接收Bug”和“Bug修复完成”，持续执行到具备测试复测条件：

1. 按Bug编号读取真实项目、状态、负责人、复现内容和环境；需求、开发任务、失败用例、仓库字段及代码关系存在时一并读取，不存在时记录为`无`，不得据此阻塞。
2. Bug状态必须是项目真实工作流中需要开发处理的非终态。负责人可以是任意用户，不作为门禁；不得静默改派，结果中保留并报告原负责人。
3. Bug可以没有任何关联项，也可以没有仓库字段、仓库地址或仓库关联；这些缺失本身不再触发零写入停止。
4. 从当前工作区、Bug描述、复现路径、页面URL或接口、运行证据和当前对话定位前端、后端、数据、配置、集成或环境根因。只有复现信息/期望结果/目标环境不足，或多个候选代码库证据冲突导致无法安全确定修改对象时才停止。
5. 从证据定位出的前端`develop`或后端`dev`创建/复用`fix/BUG-123`，分支和MR必须正式关联Bug本身；已有且可验证的需求、开发任务和原失败用例关系继续保留并关联，没有则不补造、不阻塞。
6. 完成最小范围修复，验证原失败路径、边界值和必要相邻路径。
7. 获取最新代码，重跑检查，提交、推送并创建/复用MR。
8. MR创建后不读取、不等待评审、CI或讨论状态，直接尝试合并到已核验的真实集成分支；允许自动批准自己的MR。代码冲突、目标分支错误、技术上不可合并或平台拒绝时停止，不强推、不使用管理员绕过、不关闭保护规则。
9. 协调或验证test环境已包含修复版本；本Skill不得修改生产流水线。
10. 证据完整后只把Bug改为`已修复`，再交`$yunxiao-test-management`执行原用例复测；开发不关闭Bug、不写复测通过。

同一命令重试时从最后一个已验证检查点继续，不重复建分支、MR或覆盖证据。

## 批量修复本人Bug

标准命令：

```text
/skill yunxiao-development-delivery
/go 修复负责人是我的所有Bug
```

以下语义相同的表达进入同一批量处理器：

```text
/skill yunxiao-development-delivery
/go 修复我负责的全部Bug
```

```text
/skill yunxiao-development-delivery
/go 处理所有分配给我的Bug
```

执行约定：

1. 唯一解析当前登录账号。
2. 查询负责人为当前账号且当前状态需要开发处理的Bug；排除已删除、已归档、已取消、已关闭、`已修复`或等待测试复测的Bug。
3. 固定并先展示本次Bug列表；运行期间新分配的Bug留到下一批。
4. 逐条调用：

```text
/skill yunxiao-development-delivery
修复bug:<BUG-ID>
```

5. 每个Bug使用独立worktree或等价隔离工作区。
6. 单个Bug门禁失败时记录原因并继续下一个，不放宽该Bug的门禁。
7. 全部Bug均尝试后，分别列出已完成、待测试、阻塞和未修复Bug。
8. 仍有未修复或阻塞Bug时，批量目标保持未完成。

## 查询

```text
查关联代码：ONEOSP-123
查开发门禁：ONEOSP-123

查多仓库完成情况：ONEOSP-123
```

## 门禁失败回报

每条口令先校验再执行。失败统一返回：

```text
未执行：<口令/节点>
失败门禁：<检查项>
当前值：<真实值>
期望值：<允许值>
未执行动作：<本次没有执行的写操作>
原因：<为什么会造成错误流转>
处理建议：<补齐方法或正确口令>
```

门禁失败时不得创建任务、分支、MR，不得修改状态，也不得用“已处理”替代失败结论。

## 测试交接口令

```text
/skill yunxiao-test-management
提交测试:ONEOSP-123 test流水线=oneos-web-test 执行ID=PIPE-123
```
