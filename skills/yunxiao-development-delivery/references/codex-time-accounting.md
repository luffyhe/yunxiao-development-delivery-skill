# Codex对话时长与开发完成工作日志

## 1. 执行位置

只在`/go 完成开发:任务=<开发任务ID>`中执行，并且必须满足：

```text
全部适用仓库已取得可信交付版本（普通模式为已合并MR；隔离快速模式为`oneos.rapid-delivery/v1`远端源提交）
且 已记录每个MR关联当前需求和开发任务的尝试结果
且 第二轮验证和Bug闭环已经通过
```

工作日志写入和任务完成顺序固定为：

```text
确定精确实际开始时间和实际完成时间
→ 枚举关联Codex任务和分段
→ 汇总主动执行秒数
→ 换算分钟和小时
→ 创建或更新实际工时工作日志
→ 回读工作日期、实际工时、人员和工作描述
→ 保存审计证据
→ 开发任务进入已完成
```

任一统计或工作日志门禁失败时，不把开发任务改为`已完成`。

## 2. 精确开始与完成时间

1. 从当前开发任务、需求、分支、提交、MR创建记录和本次执行证据枚举全部适用MR；不要求关联成功。
2. 普通模式验证每个MR目标分支正确并已经合并；隔离快速模式验证MR目标分支正确、无冲突、仅因评审门禁未合并，且远端源分支HEAD等于交付提交。
3. 普通模式读取每个MR的可信`merged_at`；隔离快速模式读取每个远端交付提交的可信提交时间。
4. 多仓库场景取所有适用交付版本中最晚的来源时间；单仓库取该版本的来源时间。
5. 实际开始时间优先读取开始开发时保存的专用字段；无专用字段时读取首次`[开发开始]`评论或首次合法进入`处理中`的工作项动态。后续重试不得覆盖。
6. 按云效项目时区转换开始和完成时间，在实际工时记录的`工作描述`中同时保存精确到秒的两个ISO时间戳。
7. `工作日期`只保存开始和完成的自然日期：`gmt-start=实际开始日期`、`gmt-end=实际完成日期`；不得用日期值冒充精确时间。

禁止使用当前命令时间、流水线时间、第一条MR合并时间或手工估算时间替代。普通模式不得用提交时间替代合并时间；仅满足`rapid-flow.md`的隔离快速模式可使用已回读远端交付提交的可信提交时间。

## 3. Codex任务关联规则

枚举当前可访问的Codex任务，只有满足以下任一证据的任务或分段才能计入：

- `/go 开发任务:任务=<当前开发任务ID>`，或其带`输出执行方案`且已在同一Codex任务中确认执行的模式。
- `/go 完成开发:任务=<当前开发任务ID>`。
- `修复bug:<BUG-ID>`且该Bug正式关联当前开发任务。
- 批量目标中明确记录了当前开发任务ID的独立执行分段。
- Codex任务目标、结构化交接或云效开发任务评论中保存了双方任务ID的明确映射。

只有需求编号、相似标题、相同仓库、相同分支或同一负责人不足以建立关联。每条计入记录必须保存：

```text
Codex任务ID
Codex任务标题或目标
关联依据
分段ID（若有）
主动执行开始/结束检查点
主动执行秒数
```

按`Codex任务ID + 分段ID`去重。重试和续跑可分别计入不同分段，但同一秒数区间不得重复。

## 4. 时长口径

优先读取Codex平台或目标元数据提供的主动执行时长秒数，包括模型推理、工具执行和当前开发节点内的有效处理时间。

不计入：

- 等待用户输入、验证码、审批或外部人员评审的空闲时间。
- 任务暂停、归档或无人操作期间的时间。
- 与当前开发任务无关的对话分段。
- 已在其他分段计入的重复时间。

不得用首条消息到末条消息的自然时间差代替主动执行时长。若平台只提供自然时间跨度而无法取得主动执行时长，停止填写实际开发工时并说明能力缺口。

一个Codex任务只处理当前开发任务时，可以使用该任务的全部主动执行时长。一个Codex任务同时处理多个开发任务时，必须使用批量处理器记录的逐项开始/结束检查点或平台分段时长；无法分段时停止，不能把整段时长复制给每个开发任务。

## 5. 分钟和小时换算

先汇总全部去重后的原始秒数，再统一换算，不能逐任务先四舍五入：

```text
总秒数 = Σ每个有效任务或分段的主动执行秒数
总分钟数 = max(1, floor((总秒数 + 30) ÷ 60))，仅在总秒数>0时
未舍入小时 = 总分钟数 ÷ 60
计算工时 = 未舍入小时按HALF_UP保留2位小数
云效记录工时 = 写入计算工时后的接口回读值
```

示例：

```text
30分钟 → 0.50小时
60分钟 → 1.00小时
95分钟 → 1.58小时
125分钟 → 2.08小时
```

云效实际工时接口单位必须确认是小时。先写入两位小数计算值；若项目字段按固定精度确定性归一化（实测可能出现`0.28 → 0.3`），必须在同一工作描述中同时保留`计算工时`与`云效记录工时`，并以回读值核对工作项汇总。只有单位不明、回读不稳定、回读值无法由项目精度解释或被归一化为整数时才停止任务完成；禁止静默改数。

## 6. 工作日志写入和审计

先通过`projex-list-effort-records --id <开发任务内部ID>`读取现有记录。以`项目ID+开发任务ID+complete_time_accounting`为幂等键：没有匹配记录时调用`projex-create-effort-record`，已有唯一匹配记录时调用`projex-update-effort-record`，多条匹配时停止。固定写入：

```text
id/workitem-id = 当前开发任务内部ID
operator-id = 当前开发任务负责人用户ID
gmt-start = 实际开始时间的项目时区日期
gmt-end = 实际完成时间的项目时区日期
actual-time = 换算后的两位小数计算工时（最终以接口回读精度为准）
description = 结构化开发完成统计
```

`description`至少保留：

```text
[开发完成统计]
开发任务=<DEV-ID>
适用MR/交付版本及来源时间=<列表>
实际开始时间=<项目时区ISO时间>
实际完成时间=<项目时区时间>
Codex任务/分段=<去重列表>
总秒数=<整数>
总分钟数=<整数>
换算=<总分钟数>/60=<未舍入小时>
计算工时=<两位小数小时>
云效记录工时=<接口回读小时；若与计算工时相同也照实记录>
幂等键=<项目ID+开发任务ID+complete_time_accounting>
统计时间=<ISO时间>
```

写入后重新读取该工作项的实际工时明细，精确核对记录ID、人员、工作日期、小时和完整工作描述。平台按项目精度归一化时，先把回读值补入同一记录的工作描述，再次回读并核对工作项`实际工时`汇总；不得为追求两位小数新增第二条记录。除这种已解释且已留痕的确定性精度归一化外，任何回读不一致、部分成功、幂等键重复或人员不是任务负责人都必须停止且不修改任务状态。新增Codex执行分段后允许重新汇总并更新同一记录，但必须在描述和审计证据中保留前后差异及新增来源；不得新增第二条、不得无证据手工改数。
