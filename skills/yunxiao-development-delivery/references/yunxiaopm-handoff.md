# YunxiaoPM待开发交棒适配

本文件只固化产品 Skill 与开发 Skill 之间的最小逻辑契约，不复制产品 Skill 全文。适配契约版本：`YunxiaoPM 2026-07-31`。

交接载荷仅允许：正式 Skill 名、需求/交付编号、当前状态、负责人用户 ID、正式关系回读，以及必要的材料版本、附件/MR/证据 ID、URL、哈希或幂等键。禁止定位或读取产品 Skill 的安装目录与资源；本 Skill 缺少上下文时必须按交接编号查询云效。

## 0. 唯一入口

开发Skill只有一个需求入口：`YunxiaoPM`已经完成交棒。

```text
需求=待开发
且有明确【交付】任务编号
且交付负责人=何斐
且交付ASSOCIATED→需求
```

`已确认`、`分析中`、`设计中`或`设计完成`都不是开发入口。遇到这些状态时停止，不创建`【开发】`任务，不修改需求状态，改用：

```text
/skill YunxiaoPM
交棒开发：<需求编号>；交付任务=<交付任务编号>
```

## 1. 产品Skill实际终点

YunxiaoPM交棒完成时：

```text
需求状态 = 待开发
【交付】任务编号 = 明确的ONEOS编号
【交付】负责人 = 何斐
【交付】 ASSOCIATED→需求
【开发】任务 = 不创建
【测试】任务 = 不创建
```

需求描述的`## 工作项编号（系统）`记录交付、分析、设计编号。后续定位优先级：

```text
口令显式编号 > 工作项编号（系统） > 按正式关系反查
```

禁止按标题查重或猜编号。

## 2. 三种合法交棒形态

| 形态 | 可能存在的产品任务 | 开发接收 |
|---|---|---|
| 标准路径 | 交付+分析+设计，分析/设计已收口 | 接收，不重建产品任务 |
| 无单快轨 | 交付+设计；无分析；设计当日收口 | 接收；无分析是合法结果 |
| 编号直推 | 交付+已有分析和/或设计 | 接收；缺分析或缺设计均不自动补建 |

`【交付】`描述可能仍为`等待设计任务完成后自动填入`。这不阻止产品交棒，但开发侧必须保留“材料占位”风险：只把需求的`原始诉求（AutoRDO）`作为可信输入。范围不足以编码时，要求产品补设计/AutoPRD；不得自行宣称设计材料齐全。

## 3. 接收验收

收到“需求编号+交付任务编号”后重新读取云效，逐项检查：

1. 需求编号唯一且当前状态为`待开发`。
2. 交付任务编号唯一，标题前缀为`【交付】`。
3. 交付任务负责人为何斐。
4. 交付任务通过`ASSOCIATED`正式关联该需求。
5. 需求`工作项编号（系统）`中的交付编号与口令一致；冲突或多个交付编号时停止。
6. 读取交付描述，记录“正式AutoPRD”或“占位风险”。
7. 按编号和正式关系检查现有`【开发】`任务；不按标题查重。

接收结果：

- 全部通过：`交棒已接收`。
- 已有有效开发任务：幂等复用，进入开发准备。
- 没有开发任务：这是产品Skill的正常输出，不是错误。
- 需求不是待开发、交付关系不符、负责人不符或编号冲突：停止，不自动改产品交棒数据，交回`$YunxiaoPM`。
- 交付任务已经`已完成`：视为产品验收已关闭的生命周期；所有开发命令零写入，不复用、不新建、不重开子任务，交回`$YunxiaoPM`创建新的需求/交付。

## 4. 分配开发任务

规范口令：

```text
分配任务:任务=ONEOS-456 负责人=李振 计划开始=2026-07-27 计划完成=2026-07-28 预计工时=8
```

其中`任务=ONEOS-456`固定表示来源`【交付】`任务。不要把交付任务本身改派给李振；要在它下面创建或复用开发子任务：

```text
【开发】<需求标题>
状态 = 待处理
负责人 = 尽量设置指定开发人员；无法唯一解析时可保留原值或留空
计划开始 = 口令日期
计划完成 = 口令日期
预计工时 = 可选；填写时为正数小时
正式归属 = 唯一【交付】任务树
需求追溯 = 开发任务必须直接ASSOCIATED→需求
技术方案 = 描述中的`## 技术实施方案`托管区块，绑定正式需求编号与方案哈希；不得包含`/skill`或`/go`命令
```

分配中的云效操作必须使用官方CLI带哈希的`doctor → analyze → preflight → apply`路径。复用任务时负责人唯一解析不构成门禁并可保留原值；新建任务因CLI要求`assignedTo`而必须唯一解析负责人，否则预检零写入阻塞。计划开始≤计划完成；预计工时可以不设置，设置时必须>0。交付下无开发子任务时创建；唯一有效子任务时复用；多条无法判断时要求`开发任务=<编号>`。分配时从关联需求完整说明生成技术方案；未核实的仓库、文件和范围不得编造。涉及多个开发人员时分别执行分配。

开发任务必须同时满足`TASK_SUB→【交付】`和`ASSOCIATED→需求`。经交付任务间接可达需求不算完成关联。描述中的`## 技术实施方案`区块采用幂等更新，不覆盖人工内容；旧的`## 下一阶段`命令块必须移除。

分配不会再次改变需求状态：来源需求已经是`待开发`。不得创建第二条交付任务，不得修改交付负责人、计划开始、计划完成或预计工时。只有在开发子任务字段、正式关系和技术方案全部回读通过后，才把交付任务从`待处理`更新为`已分配`；`已分配`或`处理中`只允许按显式编号幂等复用已有有效开发任务，不回退状态；`已完成`必须零写入并交回产品重新立项。

## 5. 后续轮转

```text
交棒已接收（需求=待开发）
→ 分配任务：创建/复用【开发】子任务并写负责人/计划/工时（子任务=待处理，交付=已分配，需求仍=待开发）
→ 开发人员执行“开发任务”（直接执行，或先输出方案并确认）
→ 记录首次真实开始时间
→ 逐仓库尝试关联feature/fix分支到需求和开发任务；失败记录后跳过
→ 优先由原生规则驱动开发子任务=处理中；首个子任务开工时同步交付=处理中、需求=开发中；规则不可用时直接/桥接更新并记录
→ 开发任务完成第一次开发侧自动化和真实页面验证
→ /go 完成开发再次执行最终代码开发侧复验
→ 自动提交、创建MR并尽力关联需求和开发任务
→ 不检查或等待评审、CI和讨论；禁止作者自审批并直接尝试合并全部适用仓库MR到自动发现的真实集成分支；隔离快速模式按`rapid-flow.md`处理仅评审门禁拒绝
→ 首次开始时间和最晚适用MR合并时间（隔离快速模式为远端交付提交时间）写入实际工时记录的工作描述
→ 工作日期覆盖开始/完成自然日期，关联Codex任务主动时长汇总到分钟并换算为小时写入唯一实际工时记录
→ 回读工作日期、实际工时、人员、精确时间描述和统计证据
→ 全部非取消开发任务=已完成且时间证据齐全，交付保持处理中，需求=开发完成
→ 唯一解析项目【测试主管】，创建或复用唯一【测试】任务并强制负责人用户ID与主管用户ID一致
→ 单独推动并验证需求：开发完成→待测试
→ 交给YunxiaoQA；交付容器在生产验收前保持处理中
```

分支创建或首次提交只是`开发任务`的兜底触发，不是首选效能时间。提交成功不是开发完成。

## 6. 幂等键

推荐记录：

```text
接收交棒：项目ID + 需求ID + 交付任务ID + accept_pm_handoff
分配开发任务：项目ID + 需求ID + 交付任务ID + 负责人ID + 范围(若有) + allocate_dev_task
进入开发中：项目ID + 需求ID + 开发任务ID + start_development
开发完成：项目ID + 需求ID + complete_development
创建测试任务：项目ID + 需求ID + create_test_task
```

相同事件重放时先读取真实状态和资产；已满足即按幂等成功返回。
