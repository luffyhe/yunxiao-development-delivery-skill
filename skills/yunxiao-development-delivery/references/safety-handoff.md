# 安全实施与跨角色交接

## 写入前

1. 明确组织、项目、项目ID、工作项类型、工作项编号和流程模型。
2. 把项目和迭代显示名解析为唯一ID；零个或多个匹配均停止。
3. 区分读取、规划和写入授权。文档、审计和“为什么”不授权修改。
4. 复用已登录会话或获批连接器，不记录账号、密码、Cookie、Token、OTP、Webhook密钥或私钥。
5. 备份相关规则的触发、条件、动作、顺序、启用状态和执行账号。
6. 对`/go 开发任务`，根据需求、任务、项目配置、可访问Codeup仓库、页面/API、代码关系和当前工作区自动确定目标项目；不要求当前对话提供仓库地址。证据冲突且无法安全确定修改对象时才停止。带`输出执行方案`时确认前只读，确认后先核验方案快照仍然有效；不带时直接执行但不跳过内部分析和门禁。
7. 对`修复bug:<BUG-ID>`，验证Bug状态需要开发处理、复现输入和目标环境足够。负责人、创建人、验证者、关联项和仓库信息均不构成门禁；不自动改派，也不改写验证者。有关联项时沿正式关系查需求并优先复用唯一有效需求开发分支，否则使用`fix/<BUG-ID>`；无关联项直接使用Bug分支。命令只授权该Bug及其证据定位代码库的修复和测试集成提交，不授权生产部署。
8. 对`/go 修复负责人是我的所有Bug`，先冻结Bug、目标仓库/分支和一个可覆盖全部提交组的test发布路径。修改循环只授权改Bug处理中状态、代码和本地验证，禁止提交、push、MR、合并或部署；最后统一提交阶段每个`仓库+分支`最多一个提交/MR，整批只触发一次test发布。
9. 对`/go 完成开发`，先确认可读取Codex任务主动执行时长和云效`实际完成时间`、`实际开发工时`字段。只有自然时间跨度、无法分段的混合任务或字段单位/精度不明时，不得填写或完成任务。
10. 对所有代码写节点，在写入前按`references/change-reporting.md`记录每个仓库的HEAD、分支和脏文件基线。已有用户或其他任务改动不得计入、提交、清理或宣称为当前成果。
11. 对`清理分支：发版任务=<ID>`，命令本身只授权按`references/release-branch-cleanup.md`删除该发版范围内通过全部门禁的精确分支。发布Skill无需发出信号；线下沟通不能替代实时发布、MR、工作项和远程HEAD证据。

## 线上修改

- 一次只改一个明确对象，保存后重新打开核验。
- 每个自动流转必须检查预期当前状态。开发Skill只拥有交付任务的`待处理→已分配→处理中`状态路径，不得改派交付负责人或覆盖其计划与工时；`处理中→已完成`由`YunxiaoPM`在生产验收通过后执行。
- 任何开发口令读到交付=`已完成`都必须零写入，不得回退、重开或补建子任务；新变更交回`YunxiaoPM`创建新生命周期。
- 创建开发任务时仍使用标题前缀和正式关系增强追溯；显式开始/完成开发命令不以工作项类型、标题前缀或关系缺失作为门禁。
- 标签仅表示业务模块。
- 原生规则不能读取关联任务标题或不能更新关联需求时，使用`integration_bridge`、`manual`或`not_supported`，不得伪装为原生自动化。
- 新规则不补触发历史事件；历史修复单独记录。
- 手工准备状态不能作为自动化通过证据。
- 开发侧不得设置、清空、覆盖或重新推导Bug验证人；该字段由`YunxiaoQA`在创建Bug时设置为当前测试用户。
- 批量Bug的统一提交与唯一test发布是批次级幂等动作。重复执行先回读提交组、MR和test执行ID，不得追加重复提交或第二次发布。
- 分支清理不创建线上通知、评论、待办、清理任务或自动化规则，不修改工作项状态。只使用精确分支名；禁止通配符、强推、管理员绕过、关闭保护规则和`git branch -D`。

## 验证与结果

每次写入后等待5–30秒，检查状态、正式关系、执行日志和后继规则。结果只使用：

- `通过`
- `异步通过`
- `未触发`
- `误触发`
- `阻塞`

任何节点门禁失败时必须“零写入并解释”，至少返回失败检查项、真实值、期望值、未执行动作和修复建议。不得在失败分支中自动修正前置状态或关系后继续。

所有开发、完成和Bug节点无论成功或阻塞，都要从真实Git及平台回读证据输出`实际执行操作`和`实际代码变更`。方案确认前只能输出计划内容并标注尚未执行。报告不得粘贴完整源码、大段diff、账号凭据、Token、Cookie、私钥或生产密钥。

至少执行一个负向场景：错误源状态、错误标题前缀、重复事件、部分资产完成或错误环境。开发任务缺正式关系仍是负向场景；单Bug无关联项或无仓库信息不是负向场景。

## 交接协议

交接给另一个Skill时输出：

```text
来源Skill：
目标Skill：
项目名称/ID：
迭代名称/ID：
需求编号/当前状态：
正式关联任务：
代码/测试/发布资产：
Bug负责人/状态：
批量提交组/唯一test发布执行ID：
实际执行操作：
逐文件代码变更：
已验证证据：
未完成项：
幂等键或事件ID：
允许的下一动作：
建议下一口令：
```

接收方必须重新读取真实状态，不能只相信交接文字。已满足的动作按幂等成功处理，缺失或冲突时停止。

所有建议下一口令必须显式包含：

```text
/skill <目标Skill名称>
```

### YunxiaoPM接入最小契约

```text
来源Skill：YunxiaoPM
需求编号/当前状态：<REQ-ID> / 待开发
正式关联任务：【交付】<DELIVERY-ID> / 负责人何斐 / ASSOCIATED→需求
未完成项：交付描述占位风险（若有）
允许的下一动作：开发Skill执行“分配任务”，创建或复用【开发】子任务
```

YunxiaoPM明确不创建`【开发】`/`【测试】`。接收方不得把两者缺失判为产品交棒失败，也不得补建产品阶段的交付、分析或设计任务。分配开发时不得把交付任务本身改派给开发人员。

## 状态所有权

| 范围 | 所有者 |
|---|---|
| 待处理至待开发、范围变更、生产后产品验收及交付容器关闭 | `YunxiaoPM` |
| 待开发至待测试、交付任务已分配/处理中、代码资产、缺陷修复、直接合并尝试、测试任务准备 | `yunxiao-development-delivery` |
| 待测试→测试中→测试完成、测试证据、用例与缺陷复测 | `YunxiaoQA` |
| 测试部署证据、发布中、发布完成/失败 | `yunxiao-release-operations` |
| 发版完成后的Codeup远程分支和当前机器安全本地分支清理 | `yunxiao-development-delivery`的独立`清理分支`命令 |

产品阶段到`待开发`的状态变化只由`YunxiaoPM`负责；开发Skill不得补偿或替代。开发Skill从已验收的待开发交棒开始，拥有交付任务`待处理→已分配→处理中`以及后续开发真实执行和完成结论。完成开发时先为每个开发任务回读实际完成时间和Codex换算后的实际开发工时；全部非取消开发子任务完成后保持交付=`处理中`、推进需求=`开发完成`。创建/复用测试任务前必须唯一解析源`【交付】`和项目`测试主管`。测试任务必须以`TASK_SUB`归入该交付并`ASSOCIATED`到同一产品需求；顶层任务只可在无歧义时补建子项关系，已经属于其他交付的任务不得静默换父级。显式写入并回读负责人用户ID，随后幂等写入并回读`测试建议`和`临时需求变更点`。源交付、需求关联、角色、负责人或描述任一读取/写入/回读失败，或存在影响验收但未确认的变更时，阻塞测试交接和需求`开发完成→待测试`。交付容器保持处理中，直到`YunxiaoPM`在生产验收通过后关闭。

`/go 完成开发`在MR创建后不检查或等待评审、CI和讨论状态，直接尝试合并到已核验的真实集成分支。允许自动批准自己的MR。代码冲突、错误目标分支、技术上不可合并或Codeup按当前权限/保护设置拒绝时停止并回报原始原因；不得强推、使用管理员绕过或关闭保护规则。

## 停止条件

遇到验证码、OTP、登录批准、权限提升、保护分支歧义、需求开发分支候选无法安全使用、批量Bug无法由一个test发布覆盖、同名项目/迭代/流水线无法区分、生产范围不清或证据不一致时停止对应动作并请求最少必要信息。单Bug分支无法唯一复用时允许回退到新建`fix/<BUG-ID>`；批量test路径不唯一则必须在代码写入前停止整个批次。清理命令的单分支证据不足只保留该分支；发版级证据不足则全部零删除。

## 回滚

先禁用本次新增规则或桥接入口，再恢复修改前配置。保留任务、关系、执行日志和发布证据；删除规则、任务、MR、流水线或测试资产需要单独授权。已由`清理分支：发版任务=<ID>`删除的远程分支不自动重建；如需恢复，必须从已验证Commit新建明确分支并单独授权。
