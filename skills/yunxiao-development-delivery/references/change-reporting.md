# 执行操作与代码变更强制回报

## 1. 适用节点

以下节点必须在每次用户可见回报中输出本规范，成功、部分完成、阻塞和重试均不例外：

- `分配任务:任务=<交付ID> ...`。
- `开发任务:任务=<ID>`直接执行。
- `开发任务:任务=<ID> 输出执行方案`确认后的实际执行。
- `/go 实现所有负责人是我的开发任务`及其续跑。
- `/go 完成开发:任务=<ID>`。
- `修复bug:<BUG-ID>`。
- `/go 修复负责人是我的所有Bug`及语义等价命令。

方案尚未确认时只输出`计划执行操作/计划代码变更`，不得写成已经执行。确认并执行后必须重新输出`实际执行操作/实际代码变更`。

## 2. 先记录基线

进入任何代码写入前，逐仓库记录：

```text
仓库绝对路径
worktree绝对路径
HEAD提交
当前分支
真实集成基线
git status --short
已有未提交/未跟踪文件
```

已有脏文件属于用户或其他任务，除非能够证明由当前工作项创建，否则不得计入当前任务、修改、提交或清理。批量开发为每个任务单独记录基线；批量Bug按`仓库+目标分支`记录共享worktree基线，并为每个Bug记录开始/结束diff检查点和代码位置归属。

## 3. 实际操作明细

按发生顺序列出本节点做过的所有状态变更，不只列代码：

```text
序号：
系统：云效|Git|Codeup|TestHub|流水线|本地运行环境
对象：项目/需求/任务/Bug/仓库/分支/MR/用例/执行ID
操作：
变更前：
变更后：
结果：通过|异步通过|未触发|误触发|阻塞
证据：回读值、日志、提交、MR、执行ID或命令结果
```

只读查询可合并为一项简述；创建/修改状态、字段、关系、分支、文件、提交、MR、测试记录、Bug和部署证据必须逐项列出。未执行的动作放入`未执行操作及原因`，不得混入已执行清单。

## 4. 实际代码变更清单

以当前工作项的基线和最终状态为准，使用`git status --short`、`git diff --name-status`、`git diff --stat`、`git diff --numstat`、暂存区差异、提交差异或MR差异交叉核验。逐仓库列出每一个当前工作项拥有的文件：

```text
仓库/角色：
分支/基线：
提交/MR：未提交|提交SHA|MR编号
变更类型：新增|修改|删除|重命名
文件：<仓库相对路径>
代码位置：组件/类/方法/接口/SQL/配置项/测试名
修改内容：
对应需求或Bug：
行数：+新增行/-删除行
验证：
```

要求：

1. 文件路径必须来自真实Git证据，不凭记忆列举。
2. 新增、修改、删除、重命名都要报告；用户只问“修改/新增”时也不能隐藏删除。
3. 每个文件说明“改了什么行为”和“为什么改”，不能只写“优化代码”。
4. 测试文件、数据库脚本、配置、依赖清单、类型定义和文档只要属于当前工作项，都要列出。
5. 未跟踪的新文件必须单独列出；不把构建缓存、依赖目录或其他任务文件冒充交付代码。
6. 多仓库逐仓库报告；不适用仓库明确写`不适用`。
7. 不粘贴完整源文件或大段diff，不输出凭据、Token、Cookie、私钥和生产密钥。
8. 若没有代码变更，必须写`代码变更：无`并说明原因。需求实现或代码缺陷修复通常不能在无代码变更时宣称完成；只有经证据证明是配置、数据、环境或无需改码的结果时才允许，并把实际操作完整列出。

## 5. 节点口径

### 分配任务

- 输出创建/复用开发任务、字段写入、正式关系、下一阶段命令和交付状态变化。
- 该节点不修改代码，固定输出`实际代码变更：无（仅进行云效任务分配）`。

### 开发任务

- 方案模式确认前：输出计划涉及的仓库、文件或模块、拟新增/修改内容和验证方案，明确`尚未执行`。
- 直接执行或方案确认后：输出本节点真实操作和工作区实际差异。该节点尚未提交时写`提交/MR：未提交`。
- 新增需求中的测试与Bug循环，也要把创建/修改的用例执行记录和Bug列入操作明细，把循环产生的代码变更并入文件清单。

### 批量开发

- 每个开发任务分别输出实际操作和逐文件代码清单。
- 禁止只输出“共修改N个文件”；汇总可以附加，但不能替代逐项报告。
- 阻塞任务仍输出已完成操作、当前差异和未执行动作，不能把另一个任务的文件算入。

### 完成开发

- 输出本节点执行的拉取、验证、提交、推送、MR、合并、工时回写、状态变化和测试交接。
- 代码清单既要标明本节点新增修改，也要给出该开发任务最终进入MR/提交的完整文件集合。
- 提交SHA、MR编号、目标分支和合并结果必须与逐仓库文件清单对应。

### 单个Bug

- 输出复现、定位、分支选择依据、修改、验证、提交、MR、test版本证据和Bug状态变化，并明确`验证人/验证者`未由开发侧修改。
- 逐文件说明根因修复点以及覆盖的原失败路径、边界和相邻路径。

### 批量Bug

- 每个Bug分别输出实际操作和逐文件代码清单。
- 明确拆分“修改阶段”和“统一提交阶段”：修改循环中每个Bug的记录必须写`提交/MR/test发布：未触发`。
- 按`仓库+目标分支`列出共享提交SHA、MR、合并结果及其覆盖Bug；按批次列出唯一test发布执行ID和覆盖的全部提交组。
- 每个成功Bug列出`已修复`状态回读，并明确验证者字段保持原值、开发侧未写入。
- 一个文件服务多个Bug时，在每个Bug下说明各自拥有的代码位置；无法安全拆分归属时报告冲突，不重复把整文件变更声称为多个Bug独立成果。

## 6. 阻塞与重试

节点阻塞时仍必须输出：

```text
实际执行操作：
实际代码变更：
未执行操作及原因：
当前保留的工作区/分支：
继续执行所需条件：
```

若响应中断但外部写入已经发生，重试时先回读真实状态和Git差异，再补发回报；不得为了生成回报而重复创建任务、分支、Bug、提交或MR。

## 7. 强制回报模板

```text
执行结论：完成|部分完成|阻塞|仅输出方案

实际执行操作：
1. <系统> <对象> <操作> <前→后> <结果/证据>

实际代码变更：
- <仓库>/<分支>
  - [新增|修改|删除|重命名] <相对路径>
    位置：<组件/类/方法/接口/SQL/配置/测试>
    内容：<行为变化及原因>
    行数：+N/-N
    验证：<命令或结果>

未执行操作及原因：
验证汇总：
下一条口令：
```

批量节点在每个任务或Bug下重复`实际执行操作`和`实际代码变更`，最后再给总计。未输出这两部分时，不得把该节点或批次报告为完成。
