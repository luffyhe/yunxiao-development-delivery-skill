# 开发阶段控制

## 1. 状态边界

本Skill拥有：

```text
YunxiaoPM：需求=待开发 + 【交付】任务=待处理 + 负责人何斐
→ 接收交棒
→ 分配任务：创建/复用【开发】子任务，同时关联交付和需求，填写负责人/计划/工时并写下一阶段命令；子任务=待处理，交付=已分配，需求仍=待开发
→ 开发任务：可先只读输出方案并等待确认；直接执行或确认后子任务=处理中，首个子任务开工时交付=处理中、需求=开发中
→ 全部非取消开发子任务完成：交付保持处理中，需求=开发完成
→ 唯一解析项目【测试主管】后，在源【交付】下创建/复用唯一【测试】子任务并关联需求；父交付、需求、负责人和描述全部回读
→ 产品需求：开发完成→待测试
```

首次提交可能晚于真实开工。开发人员执行`开发任务`进入写阶段是效能主口径，方案输出时间不是开工时间，分支关联只是自动兜底。

需求不是`待开发`或交付不是`待处理`时，DEV-IN-01失败：零写入并交回`$YunxiaoPM`。开发Skill不得执行TK03/TK04式补偿，不得把`已确认`或`设计完成`改为`待开发`。交付=`已完成`表示该生命周期已经产品验收关闭，任何新变更必须新建需求/交付生命周期。

## 3. oneos_delivery控制

| ID | 控制 | 开发门禁 |
|---|---|---|
| Y06 | 交付任务/需求进入开发中 | 首个开发分支已创建或复用；开发任务=处理中、交付源状态=已分配、需求源状态=待开发；需求/开发任务关联尽力执行但不构成门禁 |
| Y07 | 需求进入开发完成、交付保持处理中 | 全部非取消开发任务与MR满足完成门禁，且每条任务的时间证据已回读；交付容器留给生产验收关闭 |
| Y20 | 分配第一条开发任务 | 需求=待开发；交付=待处理/已分配；开发子任务≥1；负责人和计划字段完整；字段、关系和下一命令回读后交付=已分配 |
| Y21 | 开发汇总完成 | 非取消开发任务≥1且全部完成；所有相关MR已合并；每条任务实际完成时间和实际开发工时均已回读 |
| Y22 | 开发完成后建测试任务 | 源交付任务唯一；同需求、同交付树无有效测试任务；幂等键未处理；项目`测试主管`恰好1人；交接描述事实可确定 |
| Y23 | 测试交接就绪 | 唯一测试任务`TASK_SUB→源交付`且`ASSOCIATED→源需求`；负责人ID=测试主管ID；描述回读通过；需求=开发完成 |
| A04 | 拆分开发任务 | 每条有负责人、计划字段并归入交付任务树；仓库和范围在开发任务读取需求和代码事实时自动确定 |
| A05 | 按MR和Codex时长证据关闭开发任务 | 全仓库、目标分支和关系完整；最晚MR合并时间已写实际完成时间；关联Codex主动时长已换算为小时并回读 |
| A06 | 创建唯一测试任务 | 幂等键=`项目ID+需求ID+交付任务ID+create_test_task`；测试任务必须以`TASK_SUB`归入源交付并`ASSOCIATED`需求；负责人和描述均须回读 |
| A07 | 需求进入待测试 | 幂等键=`项目ID+需求ID+move_to_pending_test`；必须发生在A06父交付、需求关联、负责人和描述回读通过之后 |

主任务、开发任务和测试任务不能只靠“全部关联任务”聚合。原生规则无法按精确前缀过滤时用桥接。

`【交付】`是跨阶段容器。开发任务和测试任务都必须处于该交付的正式任务树中，并可追溯到需求；YunxiaoPM已经保证`【交付】 ASSOCIATED→需求`。测试任务必须同时满足`TASK_SUB→同一交付`和`ASSOCIATED→同一需求`，不能作为项目顶层任务遗留。接收时不得改交付计划开始、计划完成；开发侧只允许交付状态`待处理→已分配→处理中`。全部开发子任务完成后仍保持`处理中`，生产验收通过后由`YunxiaoPM`推进`已完成`。不得因快轨/编号直推缺少分析或设计任务而补建。

## 4. 分配任务字段

规范口令：

```text
分配任务:任务=ONEOS-456 负责人=李振 计划开始=2026-07-27 计划完成=2026-07-28 预计工时=8
```

1. `任务`固定表示`【交付】`任务，不表示开发子任务。
2. `负责人`可显式填写；复用任务时唯一解析不是门禁，不能唯一解析则保留已有负责人并报告。官方CLI创建工作项要求`assignedTo`，所以新建时负责人必须唯一解析，否则预检零写入阻塞。
3. 日期使用`YYYY-MM-DD`，计划开始不得晚于计划完成。
4. 预计工时可不设置；设置时单位为小时且必须为正数。
5. 无开发子任务时创建`【开发】<需求标题>`并以`TASK_SUB`归入交付；唯一有效子任务时复用；多条无法区分时要求显式`开发任务=<编号>`。
6. 创建或复用后必须同时验证`TASK_SUB→交付`和`ASSOCIATED→需求`；缺一即停止。
7. 在任务描述中幂等维护`## 下一阶段`区块，先写`/skill yunxiao-development-delivery`，再写且只写`/go 开发任务:任务=<开发任务编号>`；不追加类型、仓库、范围或基线参数，不覆盖人工描述。需要方案时由开发人员在命令末尾追加`输出执行方案`。
8. 写入后重新读取负责人、计划开始、计划完成、预计工时、状态、两条关系和下一阶段命令。
9. 分配后开发任务=`待处理`，需求仍=`待开发`，交付任务=`已分配`；交付负责人、计划和工时保持不变。
10. 仓库和范围不写入口令，也不从当前对话索要项目地址。`开发任务`分析需求、项目配置和代码事实自动判定目标项目。
11. 全部云效读取和写入按`yunxiao-cli-allocation.md`使用`doctor → preflight → apply`；CLI门禁失败或预检漂移时不得回退网页操作。

## 5. 开发任务、方案确认与原生规则

`/go 开发任务:任务=<ID> 输出执行方案`先完成只读需求、材料和代码分析，输出范围、实施步骤、验证、风险与回滚，随后保持目标未完成并等待确认。确认前不得记录开始时间、创建分支、修改状态或代码。收到明确确认后重新读取执行快照；内容变化时重新出方案，内容未变化才进入写阶段。`/go 开发任务:任务=<ID>`不展示方案、不等待确认，但仍在内部完成相同分析和门禁后进入写阶段。

进入写阶段后先列任务并完成`references/implementation-materials.md`中的新增/优化材料门禁。初次开始允许`任务=待处理、交付=已分配、需求=待开发`；同一需求已有兄弟开发任务开始时，允许`任务=待处理、交付=处理中、需求=开发中`，但必须验证同一交付树和先前状态证据；任务已为`处理中`时仅在首次开始记录和正式分支关系完整的情况下续跑。只有材料通过后才持久化首次真实开始时间、创建并关联分支以及修改代码。时间记录优先级：

1. 已有`实际开始时间`字段：首次写入当前时间。
2. 无该字段：写任务评论`[开发开始] 实际开始时间=<ISO时间> 执行人=<账号> 口令=开发任务`。
3. 已有首次时间：幂等复用，不覆盖。

开发任务与需求状态可优先由已启用原生规则承担：

```text
任务添加关联分支 + 状态=待处理 → 处理中
产品类需求添加关联分支 + 状态=待开发 → 开发中
```

任务规则不得依赖“开发”标签。云效原生规则可以继续使用`标题包含【开发】`，但显式`开发任务:任务=<ID>`不以标题前缀为门禁。交付任务`已分配→处理中`由本Skill在首个子任务开工证据成立后直接或桥接更新；不得使用“负责人不为空”等会误伤其他任务的宽泛规则。任一规则缺失、停用、条件失效或执行失败时不停止，改用可审计的直接更新或桥接，并明确记录实际方式。

状态规则通过后继续在同一个`/go`目标内实现和验证需求，不另建“实现需求”节点。开发范围涉及前端时使用`$apply-oneos-v2-frontend-guidelines`；涉及Java后端时使用`$alibaba-java-backend-guidelines`。

新增和优化需求实现后都必须完成与范围相称的开发侧自动化和真实页面验证。开发验证只证明实现可交测，不创建正式测试轮次、不写测试人员结论、不关闭Bug，也不推进需求测试阶段状态；正式测试由`YunxiaoQA`在测试任务准备完成后接手。

`开发任务`完成后写入：

```text
/skill yunxiao-development-delivery
/go 完成开发:任务=<开发任务ID>
```

开发任务的用户可见回报必须执行`references/change-reporting.md`：以写入前Git基线为准，输出本节点全部实际操作和每个任务拥有的新增、修改、删除、重命名文件。缺少这两部分时不能把本节点报告为完成；方案未确认时只能输出计划内容并标注尚未执行。

`/go 完成开发`必须创建独立的最终代码开发复验记录。复验失败须在开发范围内修复并重跑；通过后自动提交、推送、创建MR。逐仓库尝试关联需求和开发任务，失败记录后跳过。随后不读取或等待评审、CI、讨论状态，直接尝试合并；仅目标分支错误、代码冲突、MR技术不可合并或Codeup按当前权限/保护设置拒绝时停止。

全部适用MR合并后，必须按`references/codex-time-accounting.md`执行完成统计：最晚适用MR的`merged_at`写入当前开发任务`实际完成时间`；所有可审计关联Codex任务或批量分段的主动执行秒数去重汇总到分钟，再除以60并按HALF_UP保留两位小数写入`实际开发工时`。两个字段回读通过后当前任务才进入`已完成`；全部非取消开发任务均完成且证据齐全后，交付任务保持`处理中`、需求进入`开发完成`。

创建或复用测试任务时，在原描述中幂等维护以下唯一托管区块：

```md
## 开发交接
### 测试建议
- <核心正向、异常/边界、权限角色、前后端/数据一致性、兼容性、回归范围、环境版本和相关Bug/MR的具体建议>

### 临时需求变更点
- <已确认临时变更的原行为、变更后行为、原因、确认依据、影响和后续处理>
```

没有已确认临时变更时写`- 无（本次开发未发生已确认的临时需求变更）`。重复执行只替换该托管区块，人工描述必须保留。未确认变化不得包装成事实；若其影响验收标准，阻塞测试交接并列出待确认项。

开发任务的输入派生规则：

1. 从正式关联需求的完整标题自动判定新增或优化；语义冲突或不明确时停止。
2. 从需求标题、完整材料、受影响页面/接口/数据模型和代码事实自动判定前端、后端或全栈；不明确时停止。
3. 从需求、任务、项目配置、代码关系、可访问Codeup仓库、页面/API和当前工作区自动确定前端、后端项目；不要求对话提供地址。
4. 开发任务口令只有两个格式：

```text
/skill yunxiao-development-delivery
/go 开发任务:任务=<开发任务编号>
```

```text
/skill yunxiao-development-delivery
/go 开发任务:任务=<开发任务编号> 输出执行方案
```

## 6. 仓库和分支

逐仓库记录：仓库名、角色、项目集成、Webhook、真实集成分支、是否纳入MR门禁。

1. 前端优先使用`develop`，后端优先使用`dev`。
2. 对应名称不存在时不停止，读取并使用仓库真实集成/默认分支；不得为了满足Skill而创建不存在的基线。
3. 使用`feature/<需求编号>`或`fix/<缺陷编号>`。
4. 不直接推送保护分支，不创建不存在的集成分支。
5. 一个需求涉及多个仓库时，可在每个仓库使用同需求编号的短生命周期分支。
6. 只改前端或后端时，把另一端记录为`不适用`，不要建空任务。
7. Bug存在关联项时，先沿正式关系找到其下需求，再在同仓库查找需求或开发任务正式关联的开发分支。恰好一个分支仍存在、可写、可安全同步且关系回读一致时复用；零个、多条或冲突时使用`fix/<BUG-ID>`。
8. Bug没有关联项时直接使用`fix/<BUG-ID>`。不得只凭标题、编号或分支名相似度复用需求分支。

## 7. 代码资产尽力关联

优先级：

1. 从需求代码区域创建分支并回到需求确认。
2. Codeup创建分支/MR时显式选择需求和开发任务。
3. 缺陷修复还要关联Bug。
4. 分支名、提交说明和MR标题中的编号只作追溯兜底。

提交不判定开发完成。对每个适用仓库都尝试把分支/MR关联到需求和开发任务；能关联就关联，不能关联则记录原因并继续。关联结果、评审、CI和讨论状态都不作为合并或完成门禁。`完成开发`在MR创建后直接尝试合并到真实集成分支，允许自动批准自己的MR；仍不得强推、管理员绕过、关闭保护规则或忽略代码冲突。

## 8. 多仓库合并门禁

所有实际相关前后端仓库的分支和MR都必须执行一次需求/开发任务关联尝试并记录结果。无法关联时跳过该关联，不保留人工关联门禁，也不影响合并和完成；但不得因此漏掉真实适用仓库。

开发完成条件：

```text
非取消开发任务数量 > 0
且全部开发任务已完成
且每条开发任务实际完成时间已回读
且每条开发任务实际开发工时已回读
且所有适用仓库MR的关联尝试结果已记录
且全部MR已合并到自动发现的真实集成分支
且最终代码的开发侧编译/静态检查/自动化测试/必要真实页面复验通过
且开发侧失败、阻塞和未执行的必需验证均为0
且当前开发任务范围不存在仍需开发处理的Bug（已修复待复测不属于开发阻塞）
```

上述条件决定业务状态是否可推进；用户可见的`完成开发`节点还必须输出本节点操作、提交/MR对应关系和该开发任务最终进入提交/MR的完整逐文件清单。响应中断后只补发回报，不重复外部写入。

## 9. 缺陷修复

- 规范入口只有：

```text
/skill yunxiao-development-delivery
修复bug:<BUG-ID>
```

- 该入口合并旧的`接收Bug`和`Bug修复完成`，不得再生成或要求旧命令。
- 写入前核查Bug状态需要开发处理，并核查复现输入和目标环境足够。负责人、创建人和验证者不构成门禁，也不自动改派或改写。
- Bug允许没有需求、开发任务、原失败用例等任何关联项，也允许没有仓库字段、仓库地址或仓库关联；这些缺失不构成门禁。
- 从当前工作区、Bug内容、复现路径、页面URL或接口、运行证据和当前对话定位目标代码库。只有证据冲突且无法安全确定修改对象时才停止。
- 先证据定位前端、后端、数据、配置、集成或环境层，不猜字典编码。
- 有关联项时沿正式关系查找关联项下的需求，并优先复用该需求/开发任务在同仓库唯一有效的开发分支；找不到、存在多条或关系冲突时创建`fix/<BUG-ID>`。无关联项时直接创建`fix/<BUG-ID>`。分支/MR必须关联Bug本身；需求、开发任务和失败用例仅在已有且可验证时继续关联，不补造。
- 开发侧验证发现的问题优先在当前开发范围直接修复；若已有正式Bug，保留其真实关系并按单Bug规则处理，不创建或伪造正式QA结果。
- 修复完成后验证目标路径、空值、未知值、边界值和相邻展示/导出。
- 获取最新集成分支，执行代码检查，提交、推送、创建/复用MR；不读取或等待评审、CI、讨论状态，允许自审并直接尝试合并。代码冲突、错误目标分支、技术不可合并或平台拒绝时停止。
- 协调或验证test环境包含修复版本后，只把Bug改为`已修复`并回读状态；保持`验证人/验证者`不变。开发侧不得因该字段缺失或不符合预期而补写或阻塞。不关闭Bug，不写复测通过结果，也不修改可复用用例的生命周期状态。
- 每次回报都按`references/change-reporting.md`输出实际操作和逐文件根因修复清单；阻塞也必须报告当前差异和未执行动作。

批量入口：

```text
/skill yunxiao-development-delivery
/go 修复负责人是我的所有Bug
```

先通过工作项CLI固定并展示当前账号负责且需要开发处理的Bug快照，再通过Codeup/Flow CLI预检逐Bug目标仓库、分支和一个覆盖全部可处理分组的test运行；同时证明手动触发与自动触发不会叠加。排除已修复待复测、关闭、取消、归档和删除项。修改阶段逐Bug复现、改码和本地验证但不提交；最后本地按`仓库+目标分支`统一commit/push，再通过CLI创建/合并MR并启动或附着唯一test运行，保持每个Bug的验证者不变并改为已修复。单Bug阻塞不终止修改队列；提交、合并或唯一运行失败阻塞所有尚未收口Bug。

## 10. 发版任务分支清理

规范入口：

```text
/skill yunxiao-development-delivery
清理分支：发版任务=TASK-900
```

该命令与发布Skill解耦，由使用者按需执行。它不创建清理任务、通知、评论或规则，仅做必要读取、精确Codeup远程删除和当前机器安全本地清理。

发版级门禁：

```text
发版任务唯一且状态=已完成
且 oneos.product-acceptance/v1验收结论=通过
且 发版任务、本批需求和源交付的验收人、证据、生产执行ID、范围和幂等键一致
且 prod执行唯一且成功
且 本批需求与生产范围可核验
且 存在不可变生产Tag/Commit/制品
```

任一失败时全部零删除。发版级门禁通过后，按`references/release-branch-cleanup.md`对每个`仓库ID+精确分支名`独立检查；单分支保留不阻塞其他分支。远程清理和本地清理分开回报，其他开发人员电脑只能由其本机运行同一命令清理。

## 11. 全节点门禁与失败通知

每个接收、分配、开发任务、提交、建MR、完成、修复Bug和测试交接节点都执行：

```text
读取真实对象
→ 校验编号、项目/迭代、当前状态、负责人、该节点真正必需的正式关系、必要字段和前序证据；Bug修复不要求关联项、仓库信息、创建人或验证者，且不得改写验证者
→ 全部通过才写入
→ 任一失败则零写入并说明失败门禁、当前值、期望值、影响和处理建议
```

不得在同一次失败处理中“顺手修复”前置数据后继续。前置修复必须由有权限的正确Skill或单独授权动作完成，再重新执行原口令。

所有写节点在最终回报前还要执行：

```text
记录写前Git基线
→ 回读云效/Codeup/TestHub/流水线实际结果
→ 用Git状态、diff、提交或MR核验任务拥有的文件
→ 输出实际执行操作
→ 输出逐文件实际代码变更
```

批量节点逐任务或逐Bug重复该结构。全批次统计只是附加信息，不能替代逐项清单。

## 12. 批量执行控制

批量入口遵守`references/batch-execution.md`。当前账号ID、筛选范围和固定任务快照属于批次级门禁；材料、关系、状态、仓库、分支、代码和测试属于单任务门禁。

单任务失败只终止该任务，不终止队列。无法取得当前账号或任务快照、全局登录失效、全局权限不足或执行环境整体不可用时，才停止整个批次。多个任务修改同一仓库时必须使用独立worktree；没有隔离条件的任务记录为阻塞，不能在脏工作区切分支。

批量Bug先用Projex CLI冻结本人负责且需要开发处理的Bug列表，再用Codeup/Flow CLI预检并建立`仓库+目标分支`受控worktree组。修改循环不调用完整单Bug提交/发布处理器，禁止提交、MR和部署；最后每组本地统一commit/push，通过CLI创建/合并MR，并在全部必需组合并后启动或附着恰好一次test运行。Bug已修复待复测不进入开发快照；单Bug修改失败只终止该Bug，提交组或唯一运行失败阻塞其覆盖的全部未完成Bug。

`批次遍历完成`与`所有任务实现完成`分开报告。存在任一未实现项时，输出汇总但不得把批量`/go`目标标记为完成。

## 13. 开发负向测试

| 场景 | 期望 |
|---|---|
| 需求仍为已确认或设计完成 | 停止，交回YunxiaoPM完成待开发交棒 |
| 缺交付任务编号、负责人不是何斐或未ASSOCIATED需求 | 停止，不创建开发任务 |
| 交付任务已经`已完成` | 生命周期已由产品验收关闭；所有开发口令零写入，交回YunxiaoPM创建新需求/交付 |
| 负责人同名不唯一 | 复用任务时不阻塞并保留原负责人；新建任务因CLI要求`assignedTo`而在预检阶段零写入阻塞 |
| 日期倒置，或已填写预计工时且工时≤0 | 停止；预计工时未设置时允许继续 |
| 当前对话没有项目地址 | 不阻塞；根据需求、项目配置和代码事实自动判断目标项目 |
| 方案模式已输出但尚未确认 | 保持目标未完成；零写入等待确认，不记录真实开始时间 |
| 方案确认后需求、附件、原型、代码或目标分支发生影响执行的变化 | 旧方案和确认失效；重新输出方案等待确认 |
| 直接执行模式未向用户展示方案 | 合法；内部仍必须完成相同分析和全部门禁 |
| 开发或Bug节点只说“已处理/已修复”，未列实际操作和逐文件代码变更 | 不得报告节点完成；从真实状态和Git证据补发回报，不重复写入 |
| 批量节点只给修改文件总数 | 不得报告批次完成；逐任务或逐Bug补齐操作与文件归属 |
| 工作区开始前已有脏文件 | 记录基线并排除；不得计入、提交、清理或声称为当前任务成果 |
| 任务实际无代码变更 | 明确写`代码变更：无`及证据原因；代码需求或代码Bug通常不得据此宣称完成 |
| 需求标题无法唯一判定新增/优化 | 零写入停止，列出标题及冲突语义，不要求补`类型=`参数 |
| 需求材料无法唯一判定前端/后端/全栈 | 零写入停止，列出影响范围歧义，不要求补`范围=`参数 |
| 前端缺`develop`或后端缺`dev` | 不阻塞；使用仓库真实集成/默认分支并记录 |
| 优化需求描述为空、读取失败或无法明确实现/验收 | 零写入停止，列出具体缺失信息 |
| 新增需求没有附件、缺详细说明/HTML、缺在线原型URL | 零写入停止，列出缺失材料 |
| 新增需求本地HTML与在线URL原型不一致 | 零写入停止，逐项列出差异并要求产品确认 |
| 开发侧必需验证未执行、失败或阻塞 | 保持开发任务目标未完成，列出命令、环境、失败证据和补齐条件 |
| 完成开发复用第一次开发验证、未执行最终代码复验 | 保持完成开发目标未完成 |
| 开发验证目标不是本次代码版本 | 不执行或不采信结果，要求本地运行或test部署证据 |
| 仍存在需要开发处理的失败或Bug | 保持对应开发任务未完成；不得把未解决失败直接交给测试 |
| Bug已修复待复测 | 不阻塞开发侧Bug修复完成；交给YunxiaoQA复测，开发不得自行关闭 |
| 仅本地创建/推送无正式关系分支 | 不触发开发中 |
| 只有提交无MR | 不完成开发 |
| 多仓库只合并一个MR | 保持开发中 |
| MR目标不是真实集成分支 | 阻塞 |
| MR评审未通过、CI失败或存在未解决讨论，但目标分支正确、无代码冲突且平台允许合并 | 不读取、不等待这些状态，允许自审并直接尝试合并 |
| MR存在代码冲突、目标分支错误、技术不可合并或平台拒绝 | 停止对应仓库，记录Codeup原始原因；不强推、不管理员绕过、不关闭保护规则 |
| 全部MR已合并但缺Codex主动执行时长 | 不完成开发任务，列出缺失的Codex任务或分段证据 |
| 混合处理多个开发任务的Codex对话无法分段 | 不把整段时长重复计入，阻塞对应任务完成 |
| 仅能取得首末消息自然时间跨度 | 不填写实际开发工时，要求可审计的主动执行时长 |
| 云效实际开发工时字段不是小时或不支持两位小数 | 不静默取整，停止并报告字段配置问题 |
| 实际完成时间或实际开发工时回读不一致 | 不把开发任务改为已完成 |
| 当前开发任务完成但同交付仍有未完成开发任务 | 只完成当前开发任务；需求保持开发中、交付保持处理中；不创建测试任务 |
| 测试主管角色读取失败、无人或多人 | 阻塞测试交接；不创建新测试任务，不保留继承负责人，不推进需求到待测试；报告读取结果和候选 |
| 新测试任务默认负责人是创建人、交付负责人或开发负责人 | 必须覆盖为唯一测试主管并回读用户ID；覆盖或回读失败则阻塞 |
| 复用测试任务但现负责人不是测试主管 | 纠正为唯一测试主管并回读；不得把“负责人非空”当作通过 |
| 新测试任务建在项目顶层，未成为源交付子项 | 补建并回读`TASK_SUB→源交付`；失败则阻塞，不推进需求到待测试 |
| 复用测试任务已属于其他交付任务 | 阻塞并报告现父任务；不得静默解绑、换父级或再建重复测试任务 |
| 测试任务已是源交付子项但未关联产品需求 | 补建并回读`ASSOCIATED→源需求`；失败则阻塞 |
| 新建或复用测试任务后缺`测试建议`或`临时需求变更点`，或描述回读不一致 | 阻塞测试交接，不推进需求到待测试 |
| 复用测试任务已有人工描述 | 保留人工描述，只幂等替换唯一`## 开发交接`托管区块 |
| 本次没有已确认的临时需求变更 | 明确写`无（本次开发未发生已确认的临时需求变更）`，不得留空 |
| 存在影响验收但尚未确认的临时变化 | 不写成已确认事实；阻塞测试交接并反馈确认缺口 |
| 测试任务已创建但需求仍为开发完成 | 单独检查`开发完成→待测试`动作和日志，不把任务存在当作状态成功 |
| 分支/MR无法关联需求或开发任务 | 记录关联尝试和失败原因后跳过；不声称已关联，也不阻塞合并或完成 |
| Bug仅已修复 | 等待测试，不关闭 |
| 单Bug负责人不是当前账号 | 继续修复，不改派，结果中报告真实负责人 |
| 单Bug没有任何关联项且没有仓库信息，但工作区和复现证据能唯一定位代码库 | 继续修复；分支/MR关联Bug本身，不补造需求/任务/用例关系 |
| Bug存在关联项且关联需求有唯一有效开发分支 | 在该需求开发分支修复并提交，分支/MR同时关联Bug |
| Bug存在关联项但找不到需求开发分支，或候选多条/关系冲突 | 不猜分支；从真实集成分支创建/复用`fix/<BUG-ID>` |
| Bug不存在关联项 | 直接从真实集成分支创建/复用`fix/<BUG-ID>` |
| 单Bug缺复现步骤、期望结果或目标环境，或候选代码库证据冲突 | 零写入停止，列出缺口或冲突；不得把“无关联项/无仓库信息”单独列为失败原因 |
| 修复代码已完成但无MR或test版本证据 | 不把Bug改为已修复 |
| test版本已包含修复但验证者缺失或不是开发人员预期的人 | 保持验证者不变，照常按代码与部署门禁决定是否进入已修复；把字段问题交由YunxiaoQA检查建单路径 |
| 批量Bug中一个Bug阻塞 | 记录该Bug并继续下一项，不放宽单Bug门禁 |
| 批量Bug运行期间出现新分配Bug | 不加入当前快照，下次重新执行批量命令 |
| 批量Bug修改循环中出现commit/push/MR/部署 | 判定流程违规，停止后续提交；回读并报告已发生操作，不重复执行 |
| 批量Bug需要多个不兼容test发布路径 | 写代码前阻塞整个批次并给出兼容拆分方案 |
| 批量Bug最后一个修改完成前触发提交 | 阻塞统一提交阶段，先完成/排除剩余Bug并核验各组差异 |
| 批量Bug所有提交组合并成功 | 整批只触发一次test发布，并用同一执行ID证明覆盖全部已提交修复 |
| 唯一test发布失败 | 不把任何尚未收口Bug改为已修复，不自动触发第二次发布 |
| 发版任务为`发布完成` | 产品验收尚未关闭生命周期；`清理分支`整体零删除，并提示先由`YunxiaoPM`完成产品验收 |

| 候选只靠分支名匹配、MR未合并、合并后有新提交或生产包含无法证明 | 保留该分支并继续其他候选 |
| 候选为默认、保护、集成或长期维护分支 | 永久保留 |
| 当前机器本地分支有未推送提交、脏工作区或被worktree占用 | 不删本地分支；远程结果单独回报 |
| 需要清理其他开发人员电脑的本地分支 | 不远程操作其电脑；提示在对应开发机执行同一命令 |
| 重复开发/测试创建事件 | 复用已有有效任务 |
| 批次中一条任务材料缺失 | 记录该任务阻塞并继续下一条，不放宽材料门禁 |
| 批次运行期间出现新分配任务 | 不加入当前快照，下次新批次处理 |
| 多任务共用含未提交改动的工作区 | 阻塞后续任务，创建/复用独立worktree后再执行 |
| 快照仍有未实现任务 | 只报告遍历完成，不报告目标完成 |
