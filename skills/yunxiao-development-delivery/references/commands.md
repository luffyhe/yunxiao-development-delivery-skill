# 开发口语化口令

## 所有开发口令的统一状态边界

| 口令 | 【开发】 | 【交付】生命周期容器 | 产品需求 |
|---|---|---|---|
| `接收产品交棒` | 不创建、不修改 | 只读校验`待处理` | 只读校验`待开发` |
| `分配任务` | 创建/复用，保持`待处理` | `待处理→已分配` | 保持`待开发` |
| `开发任务`及批量实现 | `待处理→处理中` | 首个开发任务开工时`已分配→处理中` | 首个开发任务开工时`待开发→开发中` |
| `完成开发` | 当前任务满足门禁后→`已完成` | 始终保持`处理中` | 仅全部开发任务完成后`开发中→开发完成`；测试任务就绪后`开发完成→待测试` |
| 单个/批量Bug修复 | 不代改开发任务 | 不修改 | 不修改 |
| `处理发布回流` | 不代改开发任务 | 不修改 | 不修改 |
| `清理分支` | 不修改 | 不修改 | 不修改 |

开发Skill禁止执行`【交付】处理中→已完成`。生产发布后的产品验收通过，才由`YunxiaoPM`关闭该生命周期容器。若入口交付已经`已完成`，本Skill零写入并交回产品创建新的需求/交付生命周期。

单个和批量Bug修复都必须在test版本证据通过后再进入`已修复`。开发侧不得读取创建人来推导验证者，也不得设置、清空或覆盖`验证人/验证者`；该字段由`YunxiaoQA`在建缺陷时设置为当前测试用户。

## 接收产品交棒

```text
接收产品交棒:需求=ONEOSP-123 交付任务=ONEOS-456
```

先按编号读取真实状态和关系。标准输入应为需求=`待开发`、`【交付】`任务=`待处理`、负责人=何斐、交付`ASSOCIATED→需求`。本口令无论是否附带负责人、仓库或范围，都只验收交棒，不创建/复用开发任务、不改状态；下一步明确输出`分配任务`口令。

本口令只验收交棒，不分配开发任务。

## 分配任务

```text
分配任务:任务=ONEOS-456 负责人=李振 计划开始=2026-07-27 计划完成=2026-07-28 预计工时=8
```

使用空格分隔参数，不要求输入分号。`任务=ONEOS-456`固定表示YunxiaoPM交付的`【交付】`任务，`负责人=李振`表示开发任务负责人：

1. 按编号读取交付任务并反查需求，验收需求=`待开发`、交付任务=`待处理`或幂等的`已分配`交棒。
2. 尝试解析并设置李振；负责人无法唯一解析时不停止，复用任务则保留原负责人，新建任务则允许暂不设置并在结果中报告。校验日期；预计工时可不填写，填写时必须大于0。
3. 在该交付下创建或复用`【开发】<需求标题>`子任务。
4. 写负责人、计划开始、计划完成、预计工时，任务保持`待处理`。
5. 同时建立`TASK_SUB→【交付】`和`ASSOCIATED→需求`，缺少任一关系都视为分配失败。
6. 在开发任务描述中幂等维护：

```text
## 下一阶段
/skill yunxiao-development-delivery
/go 开发任务:任务=<开发任务编号>
```

不得追加类型、仓库、范围或基线参数，也不得覆盖原有业务描述。
7. 重新读取字段、两条正式关系和下一阶段命令。
8. 全部字段、正式关系和下一阶段命令回读通过后，交付任务`待处理 → 已分配`；需求保持`待开发`，开发任务保持`待处理`。交付任务仍由何斐负责，不改其计划或工时。交付=`已分配|处理中`时只允许复用已明确存在的目标开发任务，不重复创建；交付=`已完成`时零写入并交回`YunxiaoPM`开启新的生命周期。
9. 按`references/change-reporting.md`输出云效实际操作；代码固定回报`实际代码变更：无（仅进行云效任务分配）`。

仓库和前后端范围不写入口令。执行开发任务时分析需求、页面、接口、数据、项目配置、现有代码关系和可访问Codeup仓库，自动判断需要在哪个项目操作；不要求在当前对话提供项目地址。若交付下存在多条开发任务而无法判断，使用：

```text
分配任务:任务=ONEOS-456 开发任务=ONEOS-789 负责人=李振 计划开始=2026-07-27 计划完成=2026-07-28 预计工时=8
```

## 开发任务

直接执行：

```text
/skill yunxiao-development-delivery
/go 开发任务:任务=ONEOS-789
```

先输出可执行方案、讨论确认后再执行：

```text
/skill yunxiao-development-delivery
/go 开发任务:任务=ONEOS-789 输出执行方案
```

这里的`任务`表示本次要执行开发的明确工作项编号，优先使用分配后返回的`【开发】`任务，但不是开发子任务也不构成门禁。两种命令使用同一套需求、材料、代码和验证规则：

- 带`输出执行方案`：完整读取需求、附件/原型、相关代码和运行事实，输出可直接落地的方案；此时保持目标未完成，停止所有写操作并等待同一Codex任务中的明确确认，例如`确认按方案执行 ONEOS-789`。
- 收到确认后，先重新读取需求、材料和代码快照。影响实现的内容发生变化时，旧方案与旧确认立即失效，重新输出方案等待确认；未变化才继续执行。
- 不带`输出执行方案`：仍在内部完成相同分析和门禁，但不展示方案、不等待确认，直接执行。
- 确认只授权已展示且未变化的方案，不能越过材料缺失、需求不明确、环境冲突等门禁，也不能扩大范围。

方案至少反馈：

```text
需求/任务及版本快照：
新增或优化/前端后端范围：
目标项目/仓库/真实集成分支：
影响模块/页面/接口/数据：
逐步实施方案：
计划执行操作（尚未执行）：
计划新增/修改/删除/重命名的代码（尚未执行）：
分支与状态流转：
开发侧自动化测试/真实页面验证：
剩余开发失败或阻塞：
风险/回滚：
未决问题：
方案结论：可执行|不可执行
等待确认：确认按方案执行 <开发任务编号>
```

方案模式只读，不记录真实开始时间，不创建分支，不修改云效状态、代码、用例或Bug。直接模式或方案确认后在同一个开发任务节点中持续执行，不再拆分“实现需求”口令：

1. 先列出材料、开工、分支、实现、测试和回写任务。
2. 优先从正式关系读取需求完整标题；没有关系时从任务、父任务、描述、附件和项目上下文推导。标题含明确`新增/新建/增加`语义时判为新增，含明确`优化/调整/修改/修复/完善/改造`语义时判为优化；关系缺失本身不阻塞，只有材料语义冲突或无法判定类型时停止并反馈。
3. 从需求标题、完整描述/附件、受影响页面、接口、数据模型和现有代码事实自动判定前端、后端或全栈。无法唯一确定时停止并说明冲突，不要求开发人员补`范围=`参数。
4. 分析需求、任务、父任务、附件、页面、接口、数据、项目配置、现有代码关系、可访问Codeup仓库和当前工作区，自动判断前端、后端项目；不从对话索要项目地址。只有发现多个冲突候选且继续会改错项目时才停止。
5. `任务=<ID>`只要求能读取到明确工作项，不要求它是`【开发】`子任务，也不要求存在`TASK_SUB→【交付】`或`ASSOCIATED→需求`。有关系时优先使用；无关系时从任务和项目证据推导需求及范围并报告追溯缺口。初次任务通常为`需求=待开发、交付=已分配、开发任务=待处理`；同一交付下已有兄弟任务开工时允许`需求=开发中、交付=处理中、当前开发任务=待处理`；续跑按实际状态幂等处理。
6. 优化需求读取云效需求完整描述；为空、获取失败、只有占位内容或无法明确实现与验收时停止并反馈具体缺口。
7. 新增需求先下载附件，必须得到详细需求文档和HTML原型，并从需求描述取得在线原型URL；无附件、材料缺失、URL不可访问或两版原型不一致时停止并反馈证据。
8. 材料门禁通过后，初次开工记录首次真实开始时间；优先从前端`develop`、后端`dev`创建分支。对应名称不存在时不停止，读取仓库真实集成/默认分支并使用，再关联`feature/<需求或任务编号>`；合法续跑复用原时间、分支和已验证检查点。
9. 优先由云效自动化规则完成：
   - 开发任务：`待处理 → 处理中`
   - 第一个开发任务开工时，交付任务：`已分配 → 处理中`
   - 产品需求首次开工：`待开发 → 开发中`
   - 需求和交付已经因兄弟任务处于`开发中/处理中`时，只更新当前开发任务，不重复推动父级状态。
10. 等待5–30秒检查状态和日志。规则缺失、停用或失败时不停止，使用可审计的直接更新或桥接完成相同状态变化，并明确记录实际方式。
11. 按自动判定的范围加载前端/后端规范Skill，读取现有代码后直接实现需求并验证。
12. 对新增和优化需求都执行开发侧编译、静态检查、单元/集成测试和必要真实页面验证；失败时修复并重跑，环境未就绪时如实阻塞。
13. 开发验证只证明实现可交测：不得创建正式测试轮次、写测试人员结论、关闭Bug或推进需求测试阶段状态。
14. `开发任务`不提交、推送、建MR、合并或部署。通过后在任务描述中幂等写入：

```text
## 下一阶段
/skill yunxiao-development-delivery
/go 完成开发:任务=<开发任务编号>
```

正式测试执行由后续`YunxiaoQA`负责；本节点不得伪造测试计划、执行或报告。

直接执行或方案确认后的每次回报必须按`references/change-reporting.md`列出本节点`实际执行操作`和逐文件`实际代码变更`。开发任务尚未提交时明确写`提交/MR：未提交`；被门禁阻塞时仍报告已经完成的安全操作、当前差异以及未执行动作。

详细材料门禁与任务清单见`references/implementation-materials.md`。

新增和优化需求的开发验证回报必须包含：

```text
验证版本/环境：
编译、静态检查、单元/集成测试：
真实页面正向/异常/边界/回归：
失败/阻塞/未执行：
正式QA：未执行（由YunxiaoQA接手）
```

## 批量实现我的开发任务

标准口令：

```text
/go 实现所有负责人是我的开发任务
```

以下相似表达按同一入口处理：

```text
/go 实现我的全部开发任务
/go 开发我负责的所有开发任务
```

需要限定范围时：

```text
/go 实现所有负责人是我的开发任务 项目=统一运营管理平台PC端 迭代=V1.3
```

执行约定：

1. 解析当前登录云效账号，查询负责人为本人、标题以`【开发】`开头、状态为`待处理`或`处理中`的有效任务。
2. 固定本次任务快照并先输出列表；运行期间新分配任务留到下次。
3. 从任务、可用需求/父任务、材料和项目上下文自动判定类型与范围，再从项目配置、Codeup、页面/API和代码事实自动发现目标仓库与真实集成分支；不读取或要求对话提供仓库地址。
4. 逐条调用直接执行模式`/go 开发任务:任务=<开发任务编号>`，不输出方案、不等待确认，也不复制或放宽单任务规则；某任务缺少所需项目地址时只阻塞该任务并继续下一条。
5. 每条任务使用独立worktree；一个任务的未提交改动不得进入另一个任务。
6. 单个任务门禁失败时停止该任务，记录失败原因并继续下一个。
7. 全部任务均尝试后，列出完成任务以及所有未实现任务、失败门禁、当前值和处理建议。
8. 按每个开发任务分别输出`实际执行操作`和逐文件`实际代码变更`，不得只给全批次文件总数；同一文件涉及多个任务时必须标明各任务拥有的代码位置，无法拆分归属则报告冲突。
9. 只要仍有未实现任务，“实现所有”的目标就保持未完成；补齐条件后使用`/go 继续实现我的开发任务`续跑原批次。
10. 批量实现只执行各任务的`开发任务`节点，不提交、不完成开发任务、不创建【测试】、不推进需求到`开发完成/待测试`，更不得关闭【交付】。

完整规则和汇总格式见`references/batch-execution.md`。

产品交棒未完成时使用：

```text
/skill YunxiaoPM
交棒开发：ONEOSP-123；交付任务=ONEOS-456
```

## 完成开发

```text
/skill yunxiao-development-delivery
/go 完成开发:任务=ONEOS-789
```

这里的`任务`仍表示`【开发】`子任务。该节点连续完成以下动作，不拆成“提交代码”“创建MR”“自动合并MR”三个业务节点：

1. 重新读取工作项、需求/任务证据、首次真实开始时间、分支、第一次验证记录和Bug；`开发任务`执行证据缺失或不完整时不停止，在本节点补做尚未完成的分析、实现、开工回写和第一次验证。
2. 针对最终代码创建独立的开发侧复验记录，重新执行自动化检查和必要真实页面验证；不得复用第一次结果冒充本轮已执行。
3. 复验失败时在当前开发范围内修复并重跑；不得把未解决失败移交测试，也不得写正式QA通过结论。
4. 汇总全部适用仓库，获取最新真实集成分支并停止处理代码冲突；重跑本Skill范围内的代码检查后自动提交、推送、创建或复用MR。逐仓库尝试把分支/MR关联需求和开发任务；能关联就关联，不能关联则记录`跳过/失败原因`并继续，不把关联结果作为合并或完成门禁。
5. MR创建后不读取、不等待代码评审、CI结果或讨论状态，直接尝试合并到自动发现并核验过的真实集成分支；不要求新的自动合并口令。允许在Codeup支持且当前账号有权限时自动批准自己的MR，但批准不是前置条件。
6. 仅代码冲突、错误目标分支、MR技术上不可合并或Codeup按当前权限/保护设置拒绝合并时停止。记录平台原始原因；不得强推、管理员绕过或关闭保护规则。
7. 全部适用仓库MR合并后，取这些MR中最晚的`merged_at`，按项目时区写入当前开发任务`实际完成时间`。
8. 查找所有能通过当前开发任务编号、正式Bug关系或批量分段证明相关的Codex任务；按任务ID和分段ID去重，汇总平台记录的主动执行秒数。总秒数统一四舍五入到分钟，再用`总分钟数÷60`换算为两位小数小时，写入`实际开发工时`。
9. 回读实际完成时间、实际开发工时和统计证据。缺任务时长、混合任务无法分段、只能取得自然时间跨度、字段单位/精度不符或回读失败时，不把开发任务改为`已完成`。
10. 统计回读通过后，当前开发任务进入`已完成`；父`【交付】`任务保持`处理中`。
11. 重新读取同一交付树的全部非取消开发任务。仍有任一任务未完成或缺实际完成时间/实际工时时，本命令止于“当前开发任务已完成”：需求保持`开发中`、交付保持`处理中`，不创建【测试】，并列出剩余开发任务及其下一条`完成开发`口令。
12. 只有全部非取消开发任务均=`已完成`且各自时间/工时证据齐全时，才将产品需求`开发中→开发完成`；交付仍保持`处理中`。
13. 从当前开发任务和产品交棒关系唯一反查源`【交付】`任务，再读取当前项目角色并要求恰好一个`测试主管`。按同项目、同需求、同交付任务树查找可复用的唯一`【测试】`任务，不按标题单独去重。
14. 创建新测试任务时直接以`TASK_SUB`放到仍为`处理中`的该`【交付】`下；复用顶层测试任务时补建同一子项关系。测试任务已属于其他交付任务时不得静默移除或换父级，立即阻塞交测。新建或复用后还必须建立`ASSOCIATED→产品需求`，并把负责人设置为唯一测试主管。
15. 在测试任务描述中幂等创建或更新以下托管区块，不覆盖区块外的人工描述：

```md
## 开发交接
### 测试建议
- <基于需求、实现、接口/数据/权限变化、边界路径、回归范围、相关Bug/MR和环境前提生成的具体建议>

### 临时需求变更点
- <已明确确认的临时变更：原行为、变更后行为、原因、确认依据、影响和后续处理>
```

没有已确认的临时需求变更时固定写：

```text
- 无（本次开发未发生已确认的临时需求变更）
```

测试建议必须具体、可执行，不得只写“全面测试”“重点回归”等空泛内容。临时需求变更点只能来自可追溯的明确确认；存在影响验收但尚未确认的候选变更时停止交测并反馈，不得猜测或伪造。
16. 回读测试任务`TASK_SUB`父任务ID、`ASSOCIATED`需求ID、负责人用户ID和描述托管区块。父任务ID必须等于源交付任务ID，需求ID必须等于源产品需求ID，负责人必须等于唯一测试主管用户ID，两个标题和实际内容必须完整；复用任务不得产生第二个`## 开发交接`。任一写入或回读不一致时，阻塞测试交接且不推进需求到`待测试`。
17. “创建/复用测试任务”和“产品需求`开发完成 → 待测试`”是两个独立动作。两条关系、负责人和描述回读全部通过后再执行状态变化，不得用测试任务存在替代状态变化证据；状态变化后再次确认交付仍为`处理中`。
18. 写入下一阶段命令：

```text
## 下一阶段
/skill YunxiaoQA
开始测试：测试任务=<测试任务编号>；需求=<需求编号>
```

19. 按`references/change-reporting.md`输出本节点拉取、验证、提交、推送、MR、合并、工时回写、状态流转和测试任务交接的全部实际操作；逐仓库列出本开发任务最终进入提交/MR的完整文件集合，并标明本节点新增修改、提交SHA、MR和目标分支，同时回报测试任务父交付关系、需求关联、测试建议、临时需求变更点及`交付=处理中`回读。

## 修复单个Bug

```text
/skill yunxiao-development-delivery
修复bug:BUG-123
```

这一条命令合并原来的“接收Bug”和“Bug修复完成”，持续执行到具备测试复测条件：

1. 按Bug编号读取真实项目、状态、负责人、复现内容和环境。需求、开发任务、失败用例、仓库字段及代码关系存在时一并读取，不存在时记录为`无`，不得据此阻塞。不要为了修复流程读取创建人来推导验证者。
2. Bug状态必须是项目真实工作流中需要开发处理的非终态。负责人可以是任意用户，不作为门禁；不得静默改派，结果中保留并报告原负责人。
3. 从当前工作区、Bug描述、复现路径、页面URL或接口、运行证据和当前对话定位前端、后端、数据、配置、集成或环境根因。只有复现信息/期望结果/目标环境不足，或多个候选代码库证据冲突导致无法安全确定修改对象时才停止。
4. 对每个受影响仓库按以下顺序选择修复分支：
   - Bug存在关联项：沿正式关系查找关联项下的需求，再读取该需求及其开发任务已关联的远程开发分支。只有同仓库恰好一个分支仍存在、可写、可安全同步且关联关系可回读时，才复用该需求开发分支。
   - 找不到有效需求开发分支、候选多条无法唯一判断或关系证据冲突：从仓库真实集成分支创建/复用`fix/BUG-123`。
   - Bug不存在关联项：直接从仓库真实集成分支创建/复用`fix/BUG-123`。
   不得只按分支名称、需求标题或编号相似度猜测需求开发分支。
5. 选定分支和后续MR必须正式关联Bug本身；已有且可验证的需求、开发任务和原失败用例关系继续保留并关联，没有则不补造、不阻塞。
6. 完成最小范围修复，验证原失败路径、边界值和必要相邻路径。
7. 获取最新代码，重跑检查，提交、推送并创建/复用MR。
8. MR创建后不读取、不等待评审、CI或讨论状态，直接尝试合并到已核验的真实集成分支；允许自动批准自己的MR。代码冲突、目标分支错误、技术上不可合并或平台拒绝时停止，不强推、不使用管理员绕过、不关闭保护规则。
9. 协调或验证test环境已包含修复版本；本Skill不得修改生产流水线。
10. test版本证据完整后，只把Bug改为`已修复`并回读状态；保持现有`验证人/验证者`不变。该字段缺失或与开发人员预期不同都不是开发侧修复门禁，不得在本命令中补写。
11. 状态回读一致后交`YunxiaoQA`执行原路径复测；开发不关闭Bug、不写复测通过。
12. 按`references/change-reporting.md`输出复现、定位、分支选择依据、代码修改、验证、提交、MR、test版本证据和Bug状态变化；逐文件说明根因修复点、修改原因、行数和覆盖的原失败/边界/相邻路径。阻塞时也要输出已执行操作与当前差异。
13. 单Bug命令不修改产品需求、【交付】、【开发】或【测试】状态；关联对象只用于分支定位和追溯。

同一命令重试时从最后一个已验证检查点继续，不重复建分支、MR或覆盖证据。

## 批量修复本人Bug

标准命令：

```text
/skill yunxiao-development-delivery
/go 修复负责人是我的所有Bug
```

以下语义相同的表达进入同一批量处理器：

```text
/skill yunxiao-development-delivery
/go 修复我负责的全部Bug
```

```text
/skill yunxiao-development-delivery
/go 处理所有分配给我的Bug
```

执行约定：

1. 唯一解析当前登录账号。
2. 查询负责人为当前账号且当前状态需要开发处理的Bug；排除已删除、已归档、已取消、已关闭、`已修复`或等待测试复测的Bug。
3. 固定并先展示本次Bug列表；运行期间新分配的Bug留到下一批。
4. 批量命令不再循环调用完整`修复bug:<BUG-ID>`。按单Bug规则解析每个Bug的目标仓库和分支，并按`仓库+目标分支`分组；不读取创建人来推导验证者。
5. 在代码写入前，必须证明所有可处理分组可以由同一个test发布执行覆盖；无法用一次发布覆盖时整个批次零代码写入，返回建议拆分的兼容批次。
6. 修改阶段按快照逐Bug执行复现、根因定位、状态进入项目真实`处理中`（需要时）、代码修改和本地验证。多个Bug只有在仓库和目标分支完全相同时才能共享受控worktree，并为每个Bug记录独立diff边界。
7. 修改阶段禁止`git commit`、push、创建MR、合并和触发任何test发布。单个Bug门禁失败时记录原因，排除其未通过的代码差异后继续下一个，不放宽门禁。
8. 最后一个可处理Bug完成本地验证后，才进入统一提交阶段：按每个`仓库+目标分支`重新执行组合验证、获取最新代码并处理冲突，每组最多创建一个包含该组全部Bug修复的提交和一个MR，然后按平台规则尝试合并。
9. 所有必需分组合并后，整个批次只触发一次test环境发布。提交/MR/合并或该次发布失败时，不把尚未完成的Bug改为`已修复`，也不得为补偿再触发第二次test发布。
10. 单次test发布证明包含全部已提交修复后，逐Bug只把状态改为`已修复`并回读；现有`验证人/验证者`必须保持不变。某Bug状态写入失败只阻塞该Bug，不重复提交、不重复发布。
11. 全部Bug均尝试后，分别列出已完成、待测试、状态写入阻塞、代码门禁阻塞和未修复Bug，并返回共享提交/MR和唯一test执行ID。
12. 每个Bug分别输出`实际执行操作`和逐文件`实际代码变更`，同时明确哪些提交/MR/test证据由批次共享；不得以全批次汇总代替。无法安全拆分共用文件的Bug归属时报告冲突。
13. 仍有未修复或阻塞Bug时，批量目标保持未完成。
14. 批量Bug命令不修改产品需求、【交付】、【开发】或【测试】状态。

## 清理发版分支

```text
/skill yunxiao-development-delivery
清理分支：发版任务=TASK-900
```

该命令是独立、按需执行的清理入口，不依赖发布Skill发出信号。线下协作已完成时无需再创建线上通知、评论、待办或清理任务。

操作与效果：

1. 按发版任务ID读取真实`发布完成`状态、prod成功执行、本批需求和不可变生产Tag/Commit/制品。
2. 从需求、开发任务、已关闭Bug、MR和Codeup正式关系发现候选；分支名称只用于发现，不单独作为删除证据。
3. 逐仓库、逐精确分支校验MR已合并、无开放MR、合并后无新提交、变更已进入本次生产版本、工作项已完成/关闭、非保护/默认/集成分支且达到保留期。
4. 仅删除通过全部门禁的Codeup远程分支，并在删除后回读；已不存在按幂等成功处理。
5. 在当前命令运行机器中，对可访问仓库先`fetch --prune`，再用`git branch -d`安全清理对应本地分支。
6. 其他开发人员电脑不能远程代删，结果中提示其在自己的开发机执行同一命令。
7. 不修改需求、任务或Bug状态，不运行流水线，不创建线上协作事项，不删除Tag。
8. 发版级证据不足时全部零删除；单分支门禁失败时保留该分支并继续检查其他候选。

详细门禁、保留期和结果格式见`references/release-branch-cleanup.md`。
