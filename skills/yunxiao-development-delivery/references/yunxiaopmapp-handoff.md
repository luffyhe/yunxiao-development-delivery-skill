# YunxiaoPMapp待开发交棒适配

本文件只固化产品Skill与开发Skill之间的最小契约，不复制产品Skill全文。适配契约版本：`YunxiaoPMapp 2026-07-24`。

## 0. 唯一入口

开发Skill只有一个需求入口：`YunxiaoPMapp`已经完成交棒。

```text
需求=待开发
且有明确【交付】任务编号
且交付负责人=何斐
且交付ASSOCIATED→需求
```

`已确认`、`分析中`、`设计中`或`设计完成`都不是开发入口。遇到这些状态时停止，不创建`【开发】`任务，不修改需求状态，改用：

```text
/skill YunxiaoPMapp
交棒开发:<需求编号> 交付任务=<交付任务编号>
```

## 1. 产品Skill实际终点

YunxiaoPMapp交棒完成时：

```text
需求状态 = 待开发
【交付】任务编号 = 明确的ONEOS编号
【交付】负责人 = 何斐
【交付】 ASSOCIATED→需求
【开发】任务 = 不创建
【测试】任务 = 不创建
```

需求描述的`## 工作项编号（系统）`记录交付、分析、设计编号。后续定位优先级：

```text
口令显式编号 > 工作项编号（系统） > 按正式关系反查
```

禁止按标题查重或猜编号。

## 2. 三种合法交棒形态

| 形态 | 可能存在的产品任务 | 开发接收 |
|---|---|---|
| 标准路径 | 交付+分析+设计，分析/设计已收口 | 接收，不重建产品任务 |
| 无单快轨 | 交付+设计；无分析；设计当日收口 | 接收；无分析是合法结果 |
| 编号直推 | 交付+已有分析和/或设计 | 接收；缺分析或缺设计均不自动补建 |

`【交付】`描述可能仍为`等待设计任务完成后自动填入`。这不阻止产品交棒，但开发侧必须保留“材料占位”风险：只把需求的`原始诉求（AutoRDO）`作为可信输入。范围不足以编码时，要求产品补设计/AutoPRD；不得自行宣称设计材料齐全。

## 3. 接收验收

收到“需求编号+交付任务编号”后重新读取云效，逐项检查：

1. 需求编号唯一且当前状态为`待开发`。
2. 交付任务编号唯一，标题前缀为`【交付】`。
3. 交付任务负责人为何斐。
4. 交付任务通过`ASSOCIATED`正式关联该需求。
5. 需求`工作项编号（系统）`中的交付编号与口令一致；冲突或多个交付编号时停止。
6. 读取交付描述，记录“正式AutoPRD”或“占位风险”。
7. 按编号和正式关系检查现有`【开发】`任务；不按标题查重。

接收结果：

- 全部通过：`交棒已接收`。
- 已有有效开发任务：幂等复用，进入开发准备。
- 没有开发任务：这是产品Skill的正常输出，不是错误。
- 需求不是待开发、交付关系不符、负责人不符或编号冲突：停止，不自动改产品交棒数据，交回`$YunxiaoPMapp`。

## 4. 分配开发任务

规范口令：

```text
分配任务:任务=ONEOS-456 负责人=李振 计划开始=2026-07-27 计划完成=2026-07-28 预计工时=8
```

其中`任务=ONEOS-456`固定表示来源`【交付】`任务。不要把交付任务本身改派给李振；要在它下面创建或复用开发子任务：

```text
【开发】<需求标题>
状态 = 待处理
负责人 = 尽量设置指定开发人员；无法唯一解析时可保留原值或留空
计划开始 = 口令日期
计划完成 = 口令日期
预计工时 = 可选；填写时为正数小时
正式归属 = 唯一【交付】任务树
需求追溯 = 开发任务必须直接ASSOCIATED→需求
下一阶段 = 描述中先包含“/skill yunxiao-development-delivery”，再包含且只包含可执行的“/go 开始开发:任务=<开发任务编号>”命令
```

负责人唯一解析不构成门禁；计划开始≤计划完成；预计工时可以不设置，设置时必须>0。交付下无开发子任务时创建；唯一有效子任务时复用；多条无法判断时要求`开发任务=<编号>`。仓库和范围不写入下一阶段口令，也不要求对话提前提供项目地址：`开始开发`分析需求、项目配置和代码事实自动判定目标项目。涉及多个开发人员时分别执行分配。

开发任务必须同时满足`TASK_SUB→【交付】`和`ASSOCIATED→需求`。经交付任务间接可达需求不算完成关联。描述中的`## 下一阶段`区块采用幂等更新，不覆盖人工内容，也不写参数占位符。

分配不会再次改变需求状态：来源需求已经是`待开发`。不得创建第二条交付任务，不得修改交付负责人、计划开始、计划完成或预计工时。只有在开发子任务字段、正式关系和下一阶段命令全部回读通过后，才把交付任务从`待处理`更新为`已分配`；重放时不得把`已分配`、`处理中`或`已完成`回退。

## 5. 后续轮转

```text
交棒已接收（需求=待开发）
→ 分配任务：创建/复用【开发】子任务并写负责人/计划/工时（子任务=待处理，交付=已分配，需求仍=待开发）
→ 开发人员显式“开始开发”
→ 记录首次真实开始时间
→ 逐仓库尝试关联feature/fix分支到需求和开发任务；失败记录后跳过
→ 优先由原生规则驱动开发子任务=处理中；首个子任务开工时同步交付=处理中、需求=开发中；规则不可用时直接/桥接更新并记录
→ 开始开发完成第一次同名验证用例与Bug闭环
→ /go 完成开发再次执行同名验证用例与Bug闭环
→ 自动提交、创建MR并尽力关联需求和开发任务
→ 不检查或等待评审、CI和讨论；允许自审并直接尝试合并全部适用仓库MR到自动发现的真实集成分支
→ 最晚适用MR合并时间写入开发任务实际完成时间
→ 关联Codex任务主动时长汇总到分钟并换算为小时写入实际开发工时
→ 回读两个字段和统计证据
→ 全部非取消开发任务=已完成且时间证据齐全，交付=已完成，需求=开发完成
→ 创建或复用唯一【测试】任务；唯一测试主管存在时指派，否则保留原负责人或留空并报告
→ 单独推动并验证需求：开发完成→待测试
→ 交给测试Skill
```

分支创建或首次提交只是`开始开发`的兜底触发，不是首选效能时间。提交成功不是开发完成。

## 6. 幂等键

推荐记录：

```text
接收交棒：项目ID + 需求ID + 交付任务ID + accept_pm_handoff
分配开发任务：项目ID + 需求ID + 交付任务ID + 负责人ID + 范围(若有) + allocate_dev_task
进入开发中：项目ID + 需求ID + 开发任务ID + start_development
开发完成：项目ID + 需求ID + complete_development
创建测试任务：项目ID + 需求ID + create_test_task
```

相同事件重放时先读取真实状态和资产；已满足即按幂等成功返回。
