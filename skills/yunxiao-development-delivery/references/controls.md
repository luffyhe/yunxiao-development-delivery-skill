# 开发阶段控制

## 1. 状态边界

本Skill拥有：

```text
YunxiaoPMapp：需求=待开发 + 【交付】任务=待处理 + 负责人何斐
→ 接收交棒
→ 分配任务：创建/复用【开发】子任务，同时关联交付和需求，填写负责人/计划/工时并写下一阶段命令；子任务=待处理，交付=已分配，需求仍=待开发
→ 开始开发：子任务=处理中，首个子任务开工时交付=处理中、需求=开发中
→ 全部非取消开发子任务完成：交付=已完成，需求=开发完成
→ 创建/复用唯一【测试】任务；测试主管能唯一解析时指派，否则保留原负责人或留空并报告
→ 产品需求：开发完成→待测试
```

首次提交可能晚于真实开工。开发人员执行`开始开发`是效能主口径，分支关联只是自动兜底。

## 2. stage_tasks控制

| ID | 事件 | 必要条件 | 动作 | 方式 |
|---|---|---|---|---|

| DEV-IN-02 | 分配任务 | DEV-IN-01通过；交付=待处理/已分配；计划开始≤计划完成；预计工时不设置或>0。负责人解析不构成门禁 | 在交付下幂等创建/复用`【开发】`子任务；尝试建立关系和设置负责人；写计划/可选工时/下一阶段命令；全部回读通过后交付`待处理→已分配`；子任务保持待处理，需求保持待开发 | 桥接 |
| DEV-IN-03/TK05/R07 | `/go`开始开发、续跑、材料门禁、实现并尽力关联代码资产 | 工作项编号明确；首个子任务开工时交付=已分配且需求=待开发；后续兄弟任务允许交付=处理中且需求=开发中；项目/仓库由需求和代码事实自动判定；材料门禁通过。工作项类型、任务关系、固定分支名、代码资产关联结果和自动化规则状态均不构成门禁 | 初次记录开始并创建/关联分支，或幂等复用既有证据；代码资产能关联就关联，不能关联记录后跳过；首个子任务使子任务=处理中、交付=处理中、需求=开发中；后续兄弟任务只更新自身；原生规则不可用时直接/桥接更新；实现并验证 | 原生/桥接+执行 |

| TK06/R08 | `/go 完成开发`复验、直接合并、工时统计与MR状态变化 | 新增需求第二轮同名用例闭环；全部相关MR已合并；Codex主动时长可审计。评审、CI、讨论和需求/开发任务关联结果均不构成门禁；`开始开发`证据不完整时在本节点补做，不阻塞 | 自动补齐缺失开发步骤、提交/建MR/直接尝试合并；写实际完成时间和实际开发工时；回读后当前子任务→已完成；全部非取消开发子任务完成且证据齐全后交付→已完成、需求→开发完成 | 执行+原生/桥接 |
| TK07/R09 | 开发完成后创建测试任务 | 需求=开发完成；事件未处理；无有效测试任务。测试主管零个或多个不构成门禁 | 创建或复用唯一`【测试】`任务；唯一测试主管时指派，否则保留已有负责人或暂不设置并报告 | 桥接 |
| TK08/R10 | 测试任务准备完成 | 唯一测试任务存在、负责人和关系回读通过；需求=开发完成 | 产品需求：开发完成→待测试 | 原生/桥接 |
| DEV-BUG-01 | `修复bug:<BUG-ID>` | Bug编号唯一；状态需要开发处理；复现输入和环境足够；目标代码库可由工作区与运行证据安全定位。负责人、关联项、仓库信息、评审、CI和讨论均不构成门禁 | 连续完成复现、修复、验证、提交、MR直接合并尝试、test部署取证；Bug→已修复并交测试 | 执行 |
| DEV-BUG-02 | `/go 修复负责人是我的所有Bug` | 当前账号唯一；可处理Bug快照可读取 | 先展示列表，再逐条调用DEV-BUG-01；单项阻塞记录后继续；隔离工作区 | 调度 |

需求不是`待开发`时，DEV-IN-01失败：停止创建开发任务并交回`$YunxiaoPMapp`。开发Skill不得执行TK03/TK04式补偿，不得把`已确认`或`设计完成`改为`待开发`。

## 3. oneos_delivery控制

| ID | 控制 | 开发门禁 |
|---|---|---|
| Y06 | 交付任务/需求进入开发中 | 首个开发分支已创建或复用；开发任务=处理中、交付源状态=已分配、需求源状态=待开发；需求/开发任务关联尽力执行但不构成门禁 |
| Y07 | 交付任务/需求进入开发完成 | 全部非取消开发任务与MR满足完成门禁，且每条任务的时间证据已回读 |
| Y20 | 分配第一条开发任务 | 需求=待开发；交付=待处理/已分配；开发子任务≥1；负责人和计划字段完整；字段、关系和下一命令回读后交付=已分配 |
| Y21 | 开发汇总完成 | 非取消开发任务≥1且全部完成；所有相关MR已合并；每条任务实际完成时间和实际开发工时均已回读 |
| Y22 | 开发完成后建测试任务 | 同需求无有效测试任务；幂等键未处理；测试主管解析仅用于尽量指派 |
| Y23 | 测试交接就绪 | 唯一测试任务已关联；需求=开发完成；需求→待测试事件未处理；负责人为空不阻塞 |
| A04 | 拆分开发任务 | 每条有负责人、计划字段并归入交付任务树；仓库和范围最晚在开始开发前补齐 |
| A05 | 按MR和Codex时长证据关闭开发任务 | 全仓库、目标分支和关系完整；最晚MR合并时间已写实际完成时间；关联Codex主动时长已换算为小时并回读 |
| A06 | 创建唯一测试任务 | 幂等键=`项目ID+需求ID+create_test_task`；负责人尽量使用唯一测试主管，无法唯一解析时可留空或保留原负责人 |
| A07 | 需求进入待测试 | 幂等键=`项目ID+需求ID+move_to_pending_test`；必须发生在A06回读通过之后 |

主任务、开发任务和测试任务不能只靠“全部关联任务”聚合。原生规则无法按精确前缀过滤时用桥接。

`【交付】`是跨阶段容器。开发任务应处于该交付的正式任务树中，并可追溯到需求；YunxiaoPMapp已经保证`【交付】 ASSOCIATED→需求`。接收时不得改交付计划开始、计划完成；分配、首个子任务开工、全部子任务完成分别只允许交付状态`待处理→已分配→处理中→已完成`。不得因快轨/编号直推缺少分析或设计任务而补建。

## 4. 分配任务字段

规范口令：

```text
分配任务:任务=ONEOS-456 负责人=李振 计划开始=2026-07-27 计划完成=2026-07-28 预计工时=8
```

1. `任务`固定表示`【交付】`任务，不表示开发子任务。
2. `负责人`可显式填写，但唯一解析不是门禁；能解析时设置，不能唯一解析时保留已有负责人或让新任务暂不设置，并报告结果。
3. 日期使用`YYYY-MM-DD`，计划开始不得晚于计划完成。
4. 预计工时可不设置；设置时单位为小时且必须为正数。
5. 无开发子任务时创建`【开发】<需求标题>`并以`TASK_SUB`归入交付；唯一有效子任务时复用；多条无法区分时要求显式`开发任务=<编号>`。
6. 创建或复用后必须同时验证`TASK_SUB→交付`和`ASSOCIATED→需求`；缺一即停止。
7. 在任务描述中幂等维护`## 下一阶段`区块，先写`/skill yunxiao-development-delivery`，再写且只写`/go 开始开发:任务=<开发任务编号>`；不追加类型、仓库、范围或基线参数，不覆盖人工描述。
8. 写入后重新读取负责人、计划开始、计划完成、预计工时、状态、两条关系和下一阶段命令。
9. 分配后开发任务=`待处理`，需求仍=`待开发`，交付任务=`已分配`；交付负责人、计划和工时保持不变。
10. 仓库和范围不写入口令，也不从当前对话索要项目地址。`开始开发`分析需求、项目配置和代码事实自动判定目标项目。

## 5. 开始开发与原生规则

`/go 开始开发`先列任务并完成`references/implementation-materials.md`中的新增/优化材料门禁。初次开始允许`任务=待处理、交付=已分配、需求=待开发`；同一需求已有兄弟开发任务开始时，允许`任务=待处理、交付=处理中、需求=开发中`，但必须验证同一交付树和先前状态证据；任务已为`处理中`时仅在首次开始记录和正式分支关系完整的情况下续跑。只有材料通过后才持久化首次真实开始时间、创建并关联分支以及修改代码。时间记录优先级：

1. 已有`实际开始时间`字段：首次写入当前时间。
2. 无该字段：写任务评论`[开发开始] 实际开始时间=<ISO时间> 执行人=<账号> 口令=开始开发`。
3. 已有首次时间：幂等复用，不覆盖。

开发任务与需求状态可优先由已启用原生规则承担：

```text
任务添加关联分支 + 状态=待处理 → 处理中
产品类需求添加关联分支 + 状态=待开发 → 开发中
```

任务规则不得依赖“开发”标签。云效原生规则可以继续使用`标题包含【开发】`，但显式`开始开发:任务=<ID>`不以标题前缀为门禁。交付任务`已分配→处理中`由本Skill在首个子任务开工证据成立后直接或桥接更新；不得使用“负责人不为空”等会误伤其他任务的宽泛规则。任一规则缺失、停用、条件失效或执行失败时不停止，改用可审计的直接更新或桥接，并明确记录实际方式。

状态规则通过后继续在同一个`/go`目标内实现和验证需求，不另建“实现需求”节点。开发范围涉及前端时使用`$apply-oneos-v2-frontend-guidelines`；涉及Java后端时使用`$alibaba-java-backend-guidelines`。

新增需求实现后必须调用`$yunxiao-test-management`，在同项目、同迭代中按需求完整名称精确匹配验证用例。失败用例查重创建`[<开发任务ID>]<Bug描述>` Bug，开发修复并置`已修复`，测试复测后通过才关闭。当前同名用例全部通过、历史失败均有复测通过证据、活动Bug和已修复待复测Bug均为0，`/go 开始开发`才完成。该门禁不包含其他需求的Bug。

`/go 开始开发`完成后写入：

```text
/skill yunxiao-development-delivery
/go 完成开发:任务=<开发任务ID>
```

`/go 完成开发`必须创建独立的第二轮同名用例执行记录。第二轮失败仍使用相同Bug标题前缀和闭环门禁；通过后自动提交、推送、创建MR。逐仓库尝试关联需求和开发任务，失败记录后跳过。随后不读取或等待评审、CI、讨论状态，直接尝试合并；仅目标分支错误、代码冲突、MR技术不可合并或Codeup按当前权限/保护设置拒绝时停止。

全部适用MR合并后，必须按`references/codex-time-accounting.md`执行完成统计：最晚适用MR的`merged_at`写入当前开发任务`实际完成时间`；所有可审计关联Codex任务或批量分段的主动执行秒数去重汇总到分钟，再除以60并按HALF_UP保留两位小数写入`实际开发工时`。两个字段回读通过后当前任务才进入`已完成`；全部非取消开发任务均完成且证据齐全后，交付任务才进入`已完成`、需求才进入`开发完成`。

开始开发的输入派生规则：

1. 从正式关联需求的完整标题自动判定新增或优化；语义冲突或不明确时停止。
2. 从需求标题、完整材料、受影响页面/接口/数据模型和代码事实自动判定前端、后端或全栈；不明确时停止。
3. 从需求、任务、项目配置、代码关系、可访问Codeup仓库、页面/API和当前工作区自动确定前端、后端项目；不要求对话提供地址。
4. 开始开发口令完整格式只有：

```text
/skill yunxiao-development-delivery
/go 开始开发:任务=<开发任务编号>
```

## 6. 仓库和分支

逐仓库记录：仓库名、角色、项目集成、Webhook、真实集成分支、是否纳入MR门禁。

1. 前端优先使用`develop`，后端优先使用`dev`。
2. 对应名称不存在时不停止，读取并使用仓库真实集成/默认分支；不得为了满足Skill而创建不存在的基线。
3. 使用`feature/<需求编号>`或`fix/<缺陷编号>`。
4. 不直接推送保护分支，不创建不存在的集成分支。
5. 一个需求涉及多个仓库时，可在每个仓库使用同需求编号的短生命周期分支。
6. 只改前端或后端时，把另一端记录为`不适用`，不要建空任务。

## 7. 代码资产尽力关联

优先级：

1. 从需求代码区域创建分支并回到需求确认。
2. Codeup创建分支/MR时显式选择需求和开发任务。
3. 缺陷修复还要关联Bug。
4. 分支名、提交说明和MR标题中的编号只作追溯兜底。

提交不判定开发完成。对每个适用仓库都尝试把分支/MR关联到需求和开发任务；能关联就关联，不能关联则记录原因并继续。关联结果、评审、CI和讨论状态都不作为合并或完成门禁。`完成开发`在MR创建后直接尝试合并到真实集成分支，允许自动批准自己的MR；仍不得强推、管理员绕过、关闭保护规则或忽略代码冲突。

## 8. 多仓库合并门禁

所有实际相关前后端仓库的分支和MR都必须执行一次需求/开发任务关联尝试并记录结果。无法关联时跳过该关联，不保留人工关联门禁，也不影响合并和完成；但不得因此漏掉真实适用仓库。

开发完成条件：

```text
非取消开发任务数量 > 0
且全部开发任务已完成
且每条开发任务实际完成时间已回读
且每条开发任务实际开发工时已回读
且所有适用仓库MR的关联尝试结果已记录
且全部MR已合并到自动发现的真实集成分支
且新增需求第二轮同名验证用例全部通过
且当前开发任务范围没有Bug或全部Bug已关闭
```

## 9. 缺陷修复

- 规范入口只有：

```text
/skill yunxiao-development-delivery
修复bug:<BUG-ID>
```

- 该入口合并旧的`接收Bug`和`Bug修复完成`，不得再生成或要求旧命令。
- 写入前核查Bug状态需要开发处理，并核查复现输入和目标环境足够。负责人不构成门禁，也不自动改派。
- Bug允许没有需求、开发任务、原失败用例等任何关联项，也允许没有仓库字段、仓库地址或仓库关联；这些缺失不构成门禁。
- 从当前工作区、Bug内容、复现路径、页面URL或接口、运行证据和当前对话定位目标代码库。只有证据冲突且无法安全确定修改对象时才停止。
- 先证据定位前端、后端、数据、配置、集成或环境层，不猜字典编码。
- 创建`fix/<BUG-ID>`，分支/MR必须关联Bug本身；需求、开发任务和失败用例仅在已有且可验证时继续关联，不补造。
- `开始开发`或`完成开发`验证产生的Bug标题必须为`[<开发任务ID>]<Bug描述>`。
- 修复完成后验证目标路径、空值、未知值、边界值和相邻展示/导出。
- 获取最新集成分支，执行代码检查，提交、推送、创建/复用MR；不读取或等待评审、CI、讨论状态，允许自审并直接尝试合并。代码冲突、错误目标分支、技术不可合并或平台拒绝时停止。
- 协调或验证test环境包含修复版本后，只把Bug改为`已修复`并交测试；不关闭Bug，不写复测通过结果，也不修改可复用用例的生命周期状态。

批量入口：

```text
/skill yunxiao-development-delivery
/go 修复负责人是我的所有Bug
```

先固定并展示当前账号负责且需要开发处理的Bug快照，再逐条调用单Bug入口。排除已修复待复测、关闭、取消、归档和删除项；单Bug阻塞不终止队列。

## 10. 全节点门禁与失败通知

每个接收、分配、开始、提交、建MR、完成、修复Bug和测试交接节点都执行：

```text
读取真实对象
→ 校验编号、项目/迭代、当前状态、负责人、该节点真正必需的正式关系、必要字段和前序证据；Bug修复不要求关联项或仓库信息
→ 全部通过才写入
→ 任一失败则零写入并说明失败门禁、当前值、期望值、影响和处理建议
```

不得在同一次失败处理中“顺手修复”前置数据后继续。前置修复必须由有权限的正确Skill或单独授权动作完成，再重新执行原口令。

## 11. 批量执行控制

批量入口遵守`references/batch-execution.md`。当前账号ID、筛选范围和固定任务快照属于批次级门禁；材料、关系、状态、仓库、分支、代码和测试属于单任务门禁。

单任务失败只终止该任务，不终止队列。无法取得当前账号或任务快照、全局登录失效、全局权限不足或执行环境整体不可用时，才停止整个批次。多个任务修改同一仓库时必须使用独立worktree；没有隔离条件的任务记录为阻塞，不能在脏工作区切分支。

批量Bug遵守相同隔离原则：先冻结本人负责且需要开发处理的Bug列表，每项使用独立worktree并调用单Bug处理器。Bug已修复待复测不进入开发快照；单Bug失败只终止该Bug。

`批次遍历完成`与`所有任务实现完成`分开报告。存在任一未实现项时，输出汇总但不得把批量`/go`目标标记为完成。

## 12. 开发负向测试

| 场景 | 期望 |
|---|---|
| 需求仍为已确认或设计完成 | 停止，交回YunxiaoPMapp完成待开发交棒 |
| 缺交付任务编号、负责人不是何斐或未ASSOCIATED需求 | 停止，不创建开发任务 |
| 负责人同名不唯一 | 不阻塞；保留原负责人或新任务暂不设置，并报告 |
| 日期倒置，或已填写预计工时且工时≤0 | 停止；预计工时未设置时允许继续 |
| 当前对话没有项目地址 | 不阻塞；根据需求、项目配置和代码事实自动判断目标项目 |
| 需求标题无法唯一判定新增/优化 | 零写入停止，列出标题及冲突语义，不要求补`类型=`参数 |
| 需求材料无法唯一判定前端/后端/全栈 | 零写入停止，列出影响范围歧义，不要求补`范围=`参数 |
| 前端缺`develop`或后端缺`dev` | 不阻塞；使用仓库真实集成/默认分支并记录 |
| 优化需求描述为空、读取失败或无法明确实现/验收 | 零写入停止，列出具体缺失信息 |
| 新增需求没有附件、缺详细说明/HTML、缺在线原型URL | 零写入停止，列出缺失材料 |
| 新增需求本地HTML与在线URL原型不一致 | 零写入停止，逐项列出差异并要求产品确认 |
| 新增需求实现完成但无同项目、同迭代、同名验证用例 | 保持开始开发目标未完成，反馈测试资产缺失 |
| 完成开发复用第一次用例结果、未创建第二轮记录 | 保持完成开发目标未完成 |
| 测试目标页面不是本次代码版本 | 不执行或不采信结果，要求本地运行或test部署证据 |
| 失败用例已建Bug但未修复/未复测 | 保持目标未完成 |
| Bug仅为已修复或开发自行关闭 | 不解除门禁，必须由测试复测并写入本轮执行记录；可复用用例状态不变 |
| 仅本地创建/推送无正式关系分支 | 不触发开发中 |
| 只有提交无MR | 不完成开发 |
| 多仓库只合并一个MR | 保持开发中 |
| MR目标不是真实集成分支 | 阻塞 |
| MR评审未通过、CI失败或存在未解决讨论，但目标分支正确、无代码冲突且平台允许合并 | 不读取、不等待这些状态，允许自审并直接尝试合并 |
| MR存在代码冲突、目标分支错误、技术不可合并或平台拒绝 | 停止对应仓库，记录Codeup原始原因；不强推、不管理员绕过、不关闭保护规则 |
| 全部MR已合并但缺Codex主动执行时长 | 不完成开发任务，列出缺失的Codex任务或分段证据 |
| 混合处理多个开发任务的Codex对话无法分段 | 不把整段时长重复计入，阻塞对应任务完成 |
| 仅能取得首末消息自然时间跨度 | 不填写实际开发工时，要求可审计的主动执行时长 |
| 云效实际开发工时字段不是小时或不支持两位小数 | 不静默取整，停止并报告字段配置问题 |
| 实际完成时间或实际开发工时回读不一致 | 不把开发任务改为已完成 |
| 测试主管角色无人或多人 | 不阻塞；保留已有负责人或新任务留空，报告候选并继续交接 |
| 测试任务已创建但需求仍为开发完成 | 单独检查`开发完成→待测试`动作和日志，不把任务存在当作状态成功 |
| 分支/MR无法关联需求或开发任务 | 记录关联尝试和失败原因后跳过；不声称已关联，也不阻塞合并或完成 |
| Bug仅已修复 | 等待测试，不关闭 |
| 单Bug负责人不是当前账号 | 继续修复，不改派，结果中报告真实负责人 |
| 单Bug没有任何关联项且没有仓库信息，但工作区和复现证据能唯一定位代码库 | 继续修复；分支/MR关联Bug本身，不补造需求/任务/用例关系 |
| 单Bug缺复现步骤、期望结果或目标环境，或候选代码库证据冲突 | 零写入停止，列出缺口或冲突；不得把“无关联项/无仓库信息”单独列为失败原因 |
| 修复代码已完成但无MR或test版本证据 | 不把Bug改为已修复 |
| 批量Bug中一个Bug阻塞 | 记录该Bug并继续下一项，不放宽单Bug门禁 |
| 批量Bug运行期间出现新分配Bug | 不加入当前快照，下次重新执行批量命令 |
| 重复开发/测试创建事件 | 复用已有有效任务 |
| 批次中一条任务材料缺失 | 记录该任务阻塞并继续下一条，不放宽材料门禁 |
| 批次运行期间出现新分配任务 | 不加入当前快照，下次新批次处理 |
| 多任务共用含未提交改动的工作区 | 阻塞后续任务，创建/复用独立worktree后再执行 |
| 快照仍有未实现任务 | 只报告遍历完成，不报告目标完成 |

## 13. 开发交付给测试

必须提供：项目/迭代、需求状态=`待测试`、全部开发任务、每条任务实际完成时间、Codex统计分钟数、实际开发工时、适用仓库、MR与目标分支、需求/开发任务关联尝试结果、合并证据、唯一测试任务、测试主管负责人、`开发完成→待测试`证据、test部署执行ID或待部署项、测试范围、已知风险，以及下一条：

```text
/skill yunxiao-test-management
提交测试:需求=<需求编号> 测试任务=<测试任务编号> test流水线=<流水线> 执行ID=<执行ID或待填写>
```
