# 开始开发材料门禁与持续执行

## 1. 标准目标

开发人员使用一个持续目标完成“开始开发”和需求实现，不拆第二个业务节点：

```text
/skill yunxiao-development-delivery
/go 开始开发:任务=ONEOS-789
```

`任务`表示本次要执行开发的明确工作项编号，优先使用`【开发】`子任务，但工作项类型和标题前缀不构成门禁。这是完整入口，不追加`类型`、仓库、范围或基线参数：

- 类型：优先从正式关联需求判定；无关系时从任务、父任务、描述、附件和项目上下文推导。显式`新增/新建/增加`语义归为新增，显式`优化/调整/修改/修复/完善/改造`语义归为优化；语义冲突或不明确时停止并说明原因。
- 范围：结合需求标题、完整描述或附件、受影响页面、接口、数据模型和现有代码自动判定前端、后端或全栈；不明确时停止。
- 仓库：分析需求、任务、项目配置、可访问Codeup仓库、页面/API、现有代码关系和当前工作区自动确定，不要求当前对话提供地址。
- 基线：前端优先`develop`，后端优先`dev`；对应名称不存在时使用仓库真实集成/默认分支，不因此停止。

`/go 开始开发`表示持续执行本节点：先列出任务清单，再依次完成门禁、正式开工、编码和第一次验证。它授权在已确认范围内修改代码，但不授权提交、推送、创建或合并MR，也不授权生产操作。提交和直接合并尝试由后续同一Skill的`/go 完成开发`承担。

## 2. 总执行顺序

```text
读取工作项以及可用的需求/父任务/项目证据
→ 列出本次执行任务
→ 按需求标题判定新增/优化
→ 根据需求材料判定前端/后端/全栈
→ 自动发现目标项目、仓库和真实集成分支
→ 校验材料、状态和可安全确定的修改范围；工作项类型、关系、负责人、对话仓库地址和固定分支名不构成门禁
→ 按自动判定的新增/优化执行材料门禁
→ 材料全部通过后记录首次真实开始时间
→ 创建并关联feature分支
→ 尝试自动化状态变化；失败时直接/桥接更新并记录
→ 读取规范Skill和仓库事实
→ 分析影响范围
→ 实现前端/后端
→ 执行自动化测试和真实页面验证
→ 回写开发证据和带`/skill`的下一阶段口令
```

材料门禁属于写入前门禁。材料缺失、读取失败、内容不明确或证据冲突时，不记录开始时间、不创建分支、不改变状态、不修改代码。

## 3. 开始时列出的任务

至少列出并持续更新：

1. 读取云效工作项、可用需求/父任务/项目证据和当前状态；类型或关系缺失不阻塞。
2. 根据需求标题判定需求类型并获取对应材料。
3. 执行需求清晰度或双原型一致性门禁。
4. 自动确认前端、后端或全栈影响范围并发现适用项目；前端优先`develop`、后端优先`dev`，不存在时使用真实集成/默认分支。
5. 记录首次真实开始时间。
6. 创建开发分支并尝试关联需求和开发任务；关联失败时记录原因后继续。
7. 尝试两条自动化状态规则；不可用时直接/桥接更新并留证，不阻塞实现。
8. 读取适用开发规范和仓库约定。
9. 分析现有代码、接口、数据模型和测试。
10. 实现需求并补充自动化测试。
11. 执行编译、静态检查、单测和真实页面验证。
12. 新增需求进入测试页面，在同项目、同迭代中按需求完整名称精确匹配并执行同名验证测试用例。
13. 对失败用例自动查重创建`[<开发任务ID>]<Bug描述>` Bug，开发修复后交测试复测。
14. 循环修复与复测，直到本需求全部用例通过且全部关联Bug由测试关闭。
15. 回写实现证据、测试闭环、风险、未完成项和带`/skill`的`完成开发`口令。

只有材料和前置门禁通过后，任务5及以后才允许执行。

## 4. 优化需求

权威开发输入为云效产品需求的完整“描述”内容。

执行：

1. 优先按`ASSOCIATED→需求`读取需求；无关系时从工作项、父任务、标题、描述、附件和项目上下文推导需求材料，关系缺失本身不停止。
2. 获取完整描述，保留标题层级、列表、图片/链接文本和验收说明，不只读取摘要。
3. 描述为空、只有占位语、读取失败、权限不足或内容被截断时停止。
4. 检查描述是否足以唯一回答：
   - 当前问题或当前行为是什么。
   - 目标行为是什么。
   - 影响的页面、接口、字段、数据或角色范围是什么。
   - 触发条件、正常路径、异常路径和边界值是什么。
   - 如何验收，什么结果算通过。
5. 任一关键问题无法从描述和现有代码事实中确定时停止，不自行补需求。
6. 通过后，把描述拆成可验证的实现清单，再进入正式开工和编码。

停止反馈必须指出具体缺失项及其造成的实现歧义，例如“未说明空值展示为横杠还是零，前端展示和导出结果无法唯一确定”。

优化需求不强制要求附件或原型；若描述主动引用附件、原型或外部说明，则被引用材料自动成为必需输入，读取失败同样停止。

## 5. 新增需求

权威输入由三部分共同组成：

```text
需求附件中的详细需求说明文档
需求附件中的HTML完整原型
需求描述中的在线原型URL
```

执行：

1. 获取需求附件清单。附件为零时立即停止。
2. 下载全部相关附件到本次任务的隔离目录；压缩包只解压到该目录，不覆盖仓库文件。
3. 必须识别出可读取的详细需求说明文档和HTML原型入口。缺少任一项、存在多个入口而无法唯一选择、下载失败或解压失败时停止。
4. 从需求完整描述中提取在线原型URL。URL缺失、无法访问、需要未完成登录或目标页面无法唯一定位时停止。
5. 分别打开本地HTML原型和在线URL原型，在相同视口、相同入口和相同交互状态下比较：
   - 页面/路由和功能入口。
   - 可见字段、文案、按钮和状态。
   - 页面结构、分组、表格/表单和布局。
   - 默认、展开、弹窗、禁用、加载、异常等交互状态。
   - 与详细需求说明对应的业务流程。
6. 发现任何会影响实现或验收的差异时停止，列出本地HTML证据、在线URL证据、差异位置和需要产品确认的选择。
7. 两版原型一致后，检查详细需求说明是否包含业务规则、字段口径、权限、异常/边界和验收标准；不明确时停止。
8. 三部分材料全部一致且明确后，形成实现清单，再进入正式开工和编码。

不能因为某一版原型看起来更新就自行选择它。未取得明确产品结论前，两版不一致一律阻塞。

## 6. 规范与实现

材料通过后按范围加载：

- 前端或全栈：`$apply-oneos-v2-frontend-guidelines`。
- Java后端或全栈：`$alibaba-java-backend-guidelines`。
- 仓库含`AGENTS.md`或更具体规则时，同时遵循；发生冲突时报告并按用户要求、安全正确性和仓库约定确定优先级。

实现前先读取目标模块、相邻页面/接口、类型、数据模型和现有测试。不得只按原型新建一套与项目架构脱节的代码。

材料职责：

- 详细需求说明或优化需求描述：业务行为和验收标准。
- HTML/在线原型：新增需求的页面结构、文案、交互和视觉目标。
- 开发规范Skill：工程实现、代码质量和验证方法。
- 现有仓库事实：框架、组件、接口和兼容性约束。

需求说明与原型发生业务冲突时同样停止，不静默决定。

## 7. 新增需求测试闭环

新增需求实现和开发自测完成后，在同一个`/go 开始开发`目标内调用`$yunxiao-test-management`完成测试闭环：

1. 优先通过`ASSOCIATED→需求`取得需求ID、项目、迭代和完整名称；无关系时使用工作项、父任务和项目上下文推导并记录依据，关系缺失本身不停止。
2. 打开云效测试页面，以`项目ID + 迭代ID + 需求完整名称`为匹配键查找验证测试用例。用例名称必须与需求完整名称完全一致；不做包含、关键词、分词、相似度或人工猜测。后续测试资产Skill负责强制两边名称一致。
3. 同名用例总数必须大于0。零个时停止；多个不同用例ID全部纳入本轮，跨需求、跨迭代或多个用例包无法唯一归属时停止并列出冲突。
4. 确认测试目标页面实际包含本次代码：
   - 可使用已启动的本地真实应用；或
   - 使用有明确执行ID/版本证据的test环境。
5. test环境没有部署本次代码、部署失败或版本无法证明时停止，不在旧版本上执行并声称通过。
6. 执行全部同名验证用例，把通过、失败、阻塞或未执行记录到本次测试计划/轮次；不修改可复用用例本身的生命周期状态。
7. 每条失败用例先按`开发任务ID + 用例ID + 归一化现象`查重，再自动创建或复用Bug。标题固定为`[<开发任务ID>]<Bug描述>`，例如`[ONEOS-789]车辆来源未翻译`；Bug必须正式关联需求、开发任务和原失败用例，并包含环境、步骤、实际、期望和证据。
8. 把Bug交回开发Skill修复。开发只可把Bug标记为`已修复`，不得自行关闭Bug或写入复测通过结果。
9. 修复版本进入同一验证环境后，由测试Skill重新执行原失败用例和必要相邻路径：
   - 通过：在本次计划/轮次写入原用例的通过复测记录，Bug由测试进入项目真实关闭态。
   - 失败：在本次计划/轮次写入原用例的失败复测记录，Bug重开或回到处理中，再次进入修复循环。
   - 两种结果均保留可复用用例，不改变其启用、关闭、归档或废弃状态。
10. 循环直到以下门禁全部满足：

```text
当前需求用例总数 > 0
且 未执行 = 0
且 阻塞 = 0
且 失败 = 0
且 每个历史失败用例都有复测通过证据
且 当前需求活动Bug = 0
且 当前需求已修复待复测Bug = 0
```

“全部Bug”只统计当前新增需求及其用例范围内的Bug，不统计项目中其他需求的Bug。Bug创建、复测、用例更新和关闭遵守`$yunxiao-test-management`，代码修复遵守本开发Skill。

优化需求默认仍以开发自测完成作为本节点完成门禁；用户明确要求进入测试闭环时，可使用同一机制。

## 8. 完成边界

`/go 开始开发`持续到以下结果之一：

- `实现完成`：
  - 优化需求：代码已修改，相关自动化测试和可执行验证通过，开发任务已回写证据。
  - 新增需求：除实现完成外，当前需求用例全部通过，全部历史失败已有复测通过证据，全部当前需求Bug由测试关闭。
- `门禁阻塞`：零写入或停在已完成的安全步骤，明确失败门禁、证据、影响和补齐方法。
- `环境阻塞`：代码实现已完成，但某项验证因可证明的环境原因无法执行；不得写成验证通过。

`/go 开始开发`本身不授权提交、推送、MR、合并或部署。若第一次验证必须部署代码，目标保持未完成并明确说明环境门禁；不得将旧版本结果记为通过。

完成后必须写入带Skill选择器的下一条口令：

```text
/skill yunxiao-development-delivery
/go 完成开发:任务=ONEOS-789
```

## 9. 完成开发的再次验证与自动合并

`/go 完成开发:任务=<开发任务ID>`执行：

1. 读取`开始开发`的材料、首次开始、分支、实现、自测、第一次验证轮次和Bug证据；缺失或不完整时不停止，在本完成节点补做尚未完成的分析、实现、状态回写和第一次验证。
2. 新增需求重新使用第7节的名称规则匹配同名验证用例，创建新的复验轮次并再次执行全部用例；第一次执行结果只能作为历史证据，不能替代本次执行。
3. 本轮失败仍按`[<开发任务ID>]<Bug描述>`创建或复用Bug，循环修复和复测，直到失败、阻塞、未执行均为0，且没有当前范围Bug或全部Bug已关闭。
4. 获取自动发现仓库的真实集成分支，前端优先`develop`、后端优先`dev`；名称不存在时使用真实集成/默认分支。处理冲突并重跑自动化测试和必要真实页面验证。
5. 自动提交、推送并为每个适用仓库创建或复用MR；逐仓库尝试关联需求和开发任务，能关联就关联，不能关联就记录并跳过，不把关联成功作为门禁。
6. MR创建后不读取、不等待评审结果、CI状态或讨论状态，直接尝试合并到已核验的真实集成分支。允许自动批准自己的MR。仍要求目标分支正确、无代码冲突、MR技术上可合并且Codeup在当前权限和保护设置下接受；不得强推、管理员绕过或关闭保护规则。
7. 平台因冲突、目标分支、技术不可合并、权限或保护规则拒绝时，记录原始原因并停止对应仓库；无需新增“提交代码”“自动合并”节点。
8. 全部MR合并后，按`references/codex-time-accounting.md`取最晚适用MR合并时间写入当前开发任务`实际完成时间`，并把所有明确关联的Codex任务主动执行时长汇总到分钟、换算为两位小数小时写入`实际开发工时`。
9. 回读两个字段和统计证据后，当前开发任务才可进入`已完成`；其余非取消开发任务未完成时，父`【交付】`任务保持`处理中`。核验全部非取消开发任务均已完成且各自有完整时间字段后，父`【交付】`任务才进入`已完成`，产品需求才进入`开发完成`。
10. 创建或复用唯一`【测试】`任务；恰好一个测试主管时自动指派。零个或多个角色用户时保留已有负责人，或让新任务暂不设置负责人并报告，不停止交接。
11. 测试任务通过后，单独执行并验证产品需求`开发完成 → 待测试`；不得把任务创建成功当成状态变化成功。
12. 输出：

```text
/skill yunxiao-test-management
提交测试:需求=<需求编号> 测试任务=<测试任务编号> test流水线=<流水线> 执行ID=<执行ID或待填写>
```
